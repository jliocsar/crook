# crook — ARCHITECTURE (draft v0.1)

How the code is laid out and the patterns it follows. The _what_ and _why_ of the product live in `SPEC.md`; the repo's toolchain rules live in `AGENTS.md` and win over anything here.

## 1. Shape in one picture

```
                 @crook/domain   (ids, entities, statuses — schemas only)
                       ▲
                 @crook/protocol (Effect RPC groups: AgentLink, ClientApi)
          ┌─────────────┼─────────────────┐
   @crook/agent    @crook/hub          @crook/web
     │      │           └──────────────┬──┘
@crook/herdr  @crook/claude     @crook/state-machine (the shape of a machine, and its walker)
```

- Arrows point at dependencies. Nothing depends on an app (`agent`, `hub`, `web`), except for two leaves that each hold a value both sides must agree on: the hub reads the CSP from `@crook/web/csp/ContentSecurityPolicy`, and the hub and `@crook/release` read the web build's directory names from `@crook/web/build/WebBuild`.
- `herdr` and `claude` are libraries only the agent uses. The phone never parses a transcript or talks Herdr; it receives `domain` values.
- `state-machine` holds what every state machine is built on and the walker its tests and charts use, for the phone and the hub alike. It knows nothing of crook: no `domain` import, and only `effect` beneath it. It is a member of its own because in `domain` a `Machine` is a laptop.
- `domain`, `protocol` and `state-machine` are the only packages the PWA bundle pulls from the monorepo, so they stay free of Node/Bun-only imports.

## 2. Packages

All under `packages/*`, per the boilerplate. Scope renamed `@boilerplate/*` → `@crook/*` (root `package.json` name too).

```
packages/
  tsconfig/   @crook/tsconfig   shared TS base (exists)
  domain/     @crook/domain     branded ids, entities, statuses
  protocol/   @crook/protocol   RPC definitions + wire errors
  herdr/      @crook/herdr      Effect client for the Herdr socket API
  claude/     @crook/claude     Claude transcript locate/tail/parse + Ask derivation
  state-machine/  @crook/state-machine  the shape of a machine, and the walker its tests and charts use
  agent/      @crook/agent      per-machine daemon (compiled binary) + herdr plugin
  hub/        @crook/hub        exe.dev server (compiled binary, embeds web build)
  web/        @crook/web        PWA (React + Vite)
  release/    @crook/release    release build: compile per target, version check, installer
  frames/     @crook/frames     per-frame QA of the catalog's stories, run by hand, not shipped
```

### 2.1 `@crook/domain`

Schemas and their types, side by side (locality rule), plus the pure functions over them that more than one app needs. No services, no IO.

- Branded ids: `MachineId`, `WorkspaceId`, `TabId`, `PaneId` (herdr's `w1:p1`), `GlobalPaneId` (`<machine>/<pane>`), `TerminalId` (herdr's `terminal_id`), `HerdrConnectionId` (see `HerdrLink`), `ClaudeSessionId`, `SubagentId` (the hex in `agent-<id>.jsonl`), `IdempotencyKey`, `TranscriptOffset`. All of them live together in `Ids`.
- Entities: `Machine`, `Workspace`, `Tab`, `Pane`, `AgentRow`, `StatusBeforeHandoff`, `AgentStatus` (`idle|working|blocked|done|unknown`), `HerdrLink`, `MachineState` (one machine's whole herd), `HerdView` (all machines + connectivity), and `HerdUpdate`, which carries it to the phone one machine at a time (`HerdReplaced`, `MachineReplaced`, `MachineLeft`; §3.1).
- `MachineState.panes` lists every pane herdr shows, agent or not, so `panePresence(state, pane)` tells `agent` (in `agents`), `noAgent` (the pane is still there: Claude exited, or it never ran one) and `gone` (the pane closed). That is the chat's end card: "Claude exited" against "This pane closed" (JC-101). An agent herdr has not re-detected yet stays `unknown`, never a status carried over from before.
- `AgentRow.terminal` is herdr's `terminal_id`. It changes on every herdr server lifetime (stop, crash, handoff; spike S6, measured on herdr 0.9.5 only) while the pane id stays, so it is what scopes a pane's `stateChangeSeq`: two sequences are comparable only under the same terminal.
- `AgentRow.beforeHandoff` (`StatusBeforeHandoff`) holds the status, `statusChangedAt`, `terminal` and `stateChangeSeq` a pane had under its previous terminal. It is set when the same agent shows up under a new terminal with a known status before, and kept while the row reads `unknown` or the status it had before; the first other status drops it. It is how a handoff's re-detection, which arrives on the same herdr connection about 3 s after the resync (spike S6), is told from a real change. A pane that was already `unknown` before the handoff gets none.
- What a real Claude reads through a handoff (measured on herdr 0.9.5, 6 handoffs of one `claude` in a probe session): first `idle` at sequence 0 for about 300 ms, then `unknown` at sequence 1 for 3.2–3.4 s, then the re-detected status at sequence 2. The 4 handoffs polled every 40–150 ms all showed the `idle`/0 read; the 2 followed through the agent's own sync first read `unknown`/1. `agent` stays `claude` and `agent_session` keeps the same id on every read, the `claude` pid is the same, and its pid file resolves the same session. A `working` agent came back `working`, an `idle` one `idle`, and a `done` one (finished in a tab nobody was viewing) came back `idle` all 3 times: the handoff loses the completion. A reconnect can therefore land on either of the first two reads. Blocked through a handoff was not measured.
- The agent therefore reads any status at sequence 0 as `unknown`, whether or not it listed the agent before: herdr bumps the sequence on every detected change, so sequence 0 is the value a lifetime starts with, before anything was detected. A freshly launched `claude` reads `unknown` and then `idle` at sequence 1 (measured, same probe), so this only ever hides the handoff's `idle`/0 placeholder.
- What marks `done` seen in herdr (measured on herdr 0.9.5, one `claude` in a probe session, no TUI attached): its tab becoming the focused tab, whichever pane of the tab has focus. Focusing the tab while another pane of it was focused, and focusing the workspace whose active tab held it, both turned `done` into `idle`; an agent that finished while its tab was focused, even with another pane of it focused, went straight to `idle`. That `done` to `idle` left `state_change_seq` and `completion_seq` unchanged. A tab's `focused` is server-wide: one tab across all workspaces reads `true`. Every focus command emitted `workspace_focused`, `tab_focused` and `pane_focused` together, so the agent subscribes to `tab.focused` to re-read on one.
- A row that carries `done` from before the handoff and is re-detected `idle` stays `done` (with the stamp and seen mark from before) while its tab is not the focused one: the handoff dropped the completion, nothing marked it seen. Once a read shows its tab focused, it is published `idle` and drops `beforeHandoff`, since that is the event that would have turned herdr's own `done` into `idle`.
- A row carries anything over from the previous state (`beforeHandoff`, or the `statusChangedAt` of an unchanged status) only from the same agent: the same terminal, or a new terminal whose Claude session resolves to the one the previous row had. A handoff keeps the pane's processes and herdr keeps the reported session (measured above), so its Claude resolves to the same session; a stop or crash restores the panes as fresh shells, so a Claude started in one afterwards is a new process and starts from nothing, even when the agent's cached rows from before the restart are still there. An agent whose session does not resolve on both reads carries nothing over a handoff, and its re-detection reads as a change.
- `seenMarkOf(row)` is the pane's seen identity: the `terminal` and `stateChangeSeq` of `beforeHandoff` while the row carries one, else the row's own. A state that continues through a handoff keeps the identity it had before it.
- `MachineState.herdr` (`HerdrLink`) carries the agent's side of the herdr connection: a `connection` id the agent mints whenever it re-reads after losing herdr, and `lostAt`, set while the agent cannot reach herdr and the rest of the state is the last one it read. `isResync(previous, next)` holds when two states were read over different connections, `isHerdrLost(state)` while `lostAt` is set.
- `CrookVersion`: `major.minor.patch`, compared as numbers, so the PWA can tell an agent that is behind the hub (`isBehind`). Each app reads its own `package.json` version, and the two release under one version and bump together (AGENTS.md): a hub-only bump would show "update agent" on every machine with no newer agent to install.
- `Notifications` (built in JC-107): the four notification switches (`NotificationEvent`, `NotificationPrefs`, all on by default) and `NotificationSettings`, which adds whether the hub can deliver (`HarkDelivery`). Shared because the hub stores them and the phone's Settings screen shows them. `agentTitleOrPane` moved to `AgentRow` for the same reason: the herd card and the notification title name an agent the same way.
- `AgentPriority` (built in JC-98): the order of one machine's agents and the needs-you count, shared by the herd list and the tab badge. See "Seen and needs-you" under 2.6.
- Transcript model (built in JC-99), in `TranscriptMessage` and `Transcript`:
  - Messages: `User` (with `isMeta`, `origin`, `queued`), `Assistant` (API message id, model, stop reason, `isApiError`), `System`, plus `UnrecognizedEntry { entryType }` for a kind crook does not know, `Malformed { byteLength }` for bytes that are not an entry, and `Omitted { byteLength }` for the start of a file a tail watch skipped (`omittedUpTo(session, start)` is the chunk that carries it, from byte 0 to the tail's start, so every position rule below holds unchanged). Each carries the byte `offset` its line starts at, so the phone can key rows on it.
  - Blocks: `Text`, `Thinking`, `ToolUse` (input as JSON), `Image { mediaType, data }` (`mediaType` is `image/png` or `image/jpeg`, the only two spike 82 found), `ToolReference`, `ToolResult` (content blocks, plus the `PatchHunk`s of an edit and a `SubagentLaunch` when the result names one), and the user and system notes Claude writes as text or entries: `CompactSummary`, `TaskNotification`, `LocalCommand`, `LocalCommandOutput`, `Interruption`, `CompactBoundary` (with an optional `manual` or `auto` trigger, the two values spike 82 measured), `TurnDuration`, `Notice`. `Unrecognized { kind }` stands for a block kind crook does not know, and for an image of any other media type, so nothing unmeasured reaches an image URL.
  - `Subagent` (id, type, description, model, tool use id, parent, depth, background, finished, stopped by user). The "N running" count in a chat's background dock arrives with the chat that shows it (JC-101); the machine card's count comes from the agent, which follows every Claude pane's roster.
  - Stream values: `TranscriptPosition { session, offset }`, `TranscriptSource` (`PaneTranscript { pane }` or `SubagentTranscript { session, subagent }`), and `TranscriptEvent`: `TranscriptOpened { session }`, `TranscriptChunk { session, offset, nextOffset, messages }`, `SubagentsChanged { session, subagents }`, `TranscriptCaughtUp { session, offset }`. `positionAfter`, `continuesFrom` and `remainderAfter` are the one definition of where a stream stands, shared by agent, hub and phone. `remainderAfter(position, event)` is what of an event the holder of `position` does not have yet: a chunk that overlaps it is cut to the lines after it, an `Omitted` note it cuts through keeps the part after the position (a watch restarted from byte 0 re-tails a file that has grown, so its note can end past where the phone stands), and an `Opened` for the session it is in is nothing.
- `Ask` (built in JC-105): `PermissionAsk { id, source, tool, plugin, action, options, dialog }`, `QuestionAsk { id, source, questions, dialog }` and `UnknownAsk { id, screen }`, keyed by `AskId`. `source` names the evidence it came from (`hook`, `transcript`, `screen`). `action` is what the tool would do: `RunCommand { command }` (Bash's `tool_input.command`, never its `description`), `EditFile { filePath, oldString, newString, replaceAll, patch }`, `WriteFile { filePath, content }`, `UseTool { input }` for any other tool, and `ScreenDetail { subject, text }` when only the screen was readable. `options` are the dialog's numbered lines with the `AskChoice` each stands for (`yes`, `always`, `no`, `other`), not key sequences: the keys depend on where the cursor sits when the answer arrives, so the agent works them out then. `dialog` is the fingerprint of the dialog the ask was read from, `None` when no dialog was readable; the agent answers only while the screen shows that same dialog. `AgentRow.ask` carries the ask while the row is `blocked` and is `None` otherwise; `pendingAskSummary(row)` is the card's one line (`Bash <first line>`, `Edit <path relative to the cwd>`, the question).
- `AnswerAsk { pane, ask, answer }` (JC-105), `answer` being `Approve`, `ApproveAlways`, `Decline { message }` or `Choose { answer }`, one option label. Several questions, a multi-select question and the free-text "Something else" row are not answerable from the phone yet: a free-text answer is a `Decline` with that message. It names the `AskId` it answers, so an answer to an ask the agent no longer shows is refused instead of landing on the next dialog. Its receipt is `InputDelivered`, confirmed like any input: the row leaves `blocked`.
- Commands: the `Command` union (`Prompt { pane, text }`, `SendKeys { pane, keys }`, `RenameAgent { pane, label }`, `ClosePane { pane, confirmed }`) and `CommandReceipt` (`InputDelivered { pane, terminal, stateChangeSeq }`, `PaneRenamed { pane, label }`, `PaneClosed { pane }`). Stop is `SendKeys` with `esc`, herdr's canonical name for Escape (`interrupt(pane)`). `hasMovedSince(receipt, row)` is the phone's "done" for input: the pane shows a later `stateChangeSeq` than the one the agent read just before it sent, or a different terminal, since a sequence restarts at 0 in a new herdr lifetime and would otherwise read as "not yet" until it climbed past the old number. A rename is done once the row carries the receipt's label, a close once the pane is gone from the agents.
- Launches (JC-111): `StartAgent { kind, folder, task }` and `CreateWorktree { kind, folder, branch, task }` form `LaunchCommand`; every command that names an existing pane forms `PaneCommand`, and only those have a `targetPane`. `kind` is `claude` only in v1. `folder` must be absolute and free of control characters; `branch` has no whitespace or control characters, and git judges the rest. `task` is the first prompt, or none. The receipt is `AgentStarted { pane }`, and `hasStarted(receipt, agents)` is the phone's "done": the new pane shows among the agents, which is when the phone opens its chat.
- Places (JC-111): `MachineState.places` lists the machine's recent folders, newest first, each a `Place { folder, checkout, usedAt }`. `checkout` is `Checkout { branch }` when the folder sits in a git checkout and none outside one, so the sheet shows the branch chip only for a checkout; `branch` is the branch checked out there when the list was published, none on a detached HEAD. A folder that no longer exists, such as a removed worktree, is left out. A path typed into the folder sheet carries no checkout information, so the sheet shows the branch chip for it and the agent answers a worktree from a folder outside git with `FolderNotCheckout`, before anything is sent. `mostRecentPlace(herd)` is the new-agent sheet's default: the newest place of a machine that is online. No full branch list is published: the sheet starts from the default, a new worktree names its own branch, and one repository on the laptop has 289 branches (measured).
- `AgentRow.label` is the name the pane was given in herdr (`pane.rename`, by crook, by hand or by a labelling plugin), trimmed, and `None` when it has none or only whitespace; `title` stays Claude's own title. `RenameAgent.label` (`PaneLabel`) must be trimmed, non-empty and free of control characters, since herdr shows it in its own TUI: the phone turns an all-blank input into `None`, which clears the name. `AgentRow.createdByCrook` says whether the pane is in the agent's `CreatedPanes`, so the phone can word a close as the confirmation up front and send `confirmed: true` from the hold, rather than learning it from a refused round trip. `agentTitle(row)` is what a card and a chat header show: the label, else the title. `HerdMachine.pinned` lists the machine's pinned panes that are in its last state.
- `Audit` (built in JC-106): the pure half of the audit log, shared by agent and hub. `commandAudit(command)` names the operation and lists its arguments (written out per variant with `Match.tagsExhaustive`, so a new command fails to compile until it is audited); `applyAuditPolicy` redacts the named arguments whole and cuts each other argument to the limit (an array of texts shares one limit, and the last text kept carries the mark), counting characters rather than UTF-16 units, marking a cut with `…`; `auditExit(exit)` turns an outcome into `succeeded`, `failed` with the error's `name` (a tagged error's `name` is its tag, measured) or `Defect`, or `interrupted`.

### 2.2 `@crook/protocol`

Two `RpcGroup`s and the wire-level tagged errors. Nothing else.

- `AgentLink` — called **by the agent** on the hub (the agent dials out, so it's always the RPC client):
  - `Attach { hello }` (streaming) → `Stream<RoutedCommand>`: the hub pushes `{ id, key, command }` down this stream for as long as the connection lives. `hello` carries the agent's version as a plain string and an optional label, so a machine is never online without them. The hub reads the string as a `CrookVersion`; one it cannot read (a prerelease, say) becomes no version, which hides the update pill instead of failing the whole `Attach`.
  - `PublishState { state: MachineState, version }`
  - `CompleteCommand { id, result }`, where `result` is a `Result<CommandReceipt, AgentCommandFailure>`
  - `TranscriptDemands` (streaming) → `Stream<TranscriptDemand>`: the whole set of transcript watches the hub wants from this machine, each `{ id, source, from, tail }`, re-sent whenever a watch starts or ends. Like `Attach`, it is the hub's push channel, kept apart from `Attach` so commands and transcripts do not share a stream.
  - `PublishTranscript { watch, update }` → `void`, failing with `TranscriptOutOfStep { watch, expected }` when the update does not continue where that watch stands. `update` is a `TranscriptEvent` or `TranscriptWatchFailed { failure }`.
- `ClientApi` — called **by the PWA** on the hub:
  - `WatchHerd` (streaming) → `Stream<HerdUpdate>`: the whole `HerdView` first as `HerdReplaced`, then a `MachineReplaced` with the whole entry of each machine that changed and a `MachineLeft` for each one that left the view. `herdUpdates` makes the stream from the hub's views and `herdViews` folds it back into the view each step stood for, so nothing past the RPC client sees an update. A `HerdReplaced` arrives again only from a hub of another version.
  - `WatchTranscript { machine, source, from, tail }` (streaming) → `Stream<TranscriptEvent>`, failing with `MachineNotInHerd`, `PaneNotInHerd`, `TranscriptReadFailed`, `TranscriptResumeRejected` or `TranscriptSessionRejected`. `from` is the `{ session, nextOffset }` of the last chunk the phone holds, or null for the start. `tail` (`TranscriptTailBytes`, or null for the whole file) applies only where a file would be read from byte 0: the watch starts at the line holding the byte that many from the end, after an `Omitted` chunk for what it skipped. A resume ignores it.
  - `WatchScreen { pane }` (streaming) → `Stream<ScreenFrame>` (terminal fallback view)
  - `SendCommand { machine, key, command }` → `CommandReceipt`, failing with one tagged error per reason. One RPC carries every `Command` variant (`RenameAgent` and `ClosePane` joined in JC-112, `StartAgent` and `CreateWorktree` in JC-111; `AnswerAsk` in JC-105; pinning is not a command but the hub-only `SetPinned` below, since it never reaches an agent), so the hub routes them all the same way and a new variant changes no RPC.
  - `ForgetMachine { machine }`: offline machines only. `MarkSeen { machine, pane }` needs no idempotency key: marking the same state seen twice changes nothing.
  - `SetPinned { machine, pane, pinned }` (JC-112): one RPC for pin and unpin, idempotent like `MarkSeen`, so it needs no key. Pinning wants the pane among the agents of the machine's last state; unpinning does not, so a stale pin can always be dropped.
  - `WatchNotificationSettings` (streaming) → `Stream<NotificationSettings>`: the four switches (`approvals`, `questions`, `finished`, `liveActivity`) and whether the hub can deliver at all (`delivery`: `ready`, or `noToken` while `CROOK_HUB_HARK_TOKEN` is unset). `SetNotificationPref { event, enabled }` fails only with `HubStorageFailed`. `SendTestNotification` fails with `HarkNotConfigured`, `HarkRefused`, `HarkRateLimited`, `HarkServerFailed`, `HarkStillProcessing`, `HarkUnreachable` (a timeout included), `HarkAnswerUnreadable`, or `HarkReachedNoDevice` when Hark took it but no phone did (built in JC-107, for JC-110's screen). Not audited: they change no machine.
  - `GetAccount` → `HubAccount { email }` (JC-110): the `X-ExeDev-Email` the hub admitted at this connection's upgrade, which is the owner's. The phone never reads a header; the hub reads it once and binds it to the connection, like the actor it audits.
  - Built so far: `WatchHerd`, `ForgetMachine`, `MarkSeen`, `SetPinned`, `SendCommand`, `WatchTranscript`, `WatchNotificationSettings`, `SetNotificationPref`, `SendTestNotification`, `GetAccount`. The refusals of `ForgetMachine`, `MarkSeen` and `SetPinned` are `MachineNotInHerd`, `MachineStillConnected`, `PaneNotInHerd` and `HubStorageFailed` (the hub's database refused the write, so nothing changed).
  - The agent's own refusals (`AgentCommandFailure`) are `PaneNotAgent`, `PaneNotCreatedByCrook`, `HerdrRefusedCommand`, `HerdrUnavailable` and `CommandDeliveryUnknown`, plus five for `AnswerAsk`: `AskNotPending` (the row is not blocked on that ask, the screen no longer shows the dialog it was read from, or the same answer already went out), `AskDialogUnreadable` (the screen shows no dialog crook can read, or no cursor in it), `AskOptionUnavailable` (the dialog offers no such option), `QuestionnaireUnsupported` (several questions, a multi-select one, or one whose kind the screen alone cannot tell) and `DeclineMessageUndelivered` (Esc went out, the message did not). Every one but the last means nothing was sent; the last is remembered like `CommandDeliveryUnknown`, so a retry does not press Esc again. For a launch they are `FolderNotFound { folder }` (nothing sent), `HerdrAnswerUnreadable { method, issue }` (herdr's first snapshot did not decode, most likely a herdr and crook protocol mismatch; nothing sent), `FolderUnreadable { folder, reason }` (the folder could not be looked at, permission denied for one; nothing sent), `FolderNotCheckout { folder }` (a worktree asked for outside git; nothing sent), `AgentNotStarted { folder, worktree, code, detail }` (a pane was opened and Claude did not come up in it; `worktree` is the checkout a `CreateWorktree` left on disk, and the message names it only then) and `TaskNotDelivered { pane, code, detail }` (Claude runs, its first prompt was refused).
- Serialization: `RpcSerialization.layerNdjson` (sockets need framing).

Why "agent is always the client": Effect RPC servers listen; the agent can't (laptop behind NAT, no inbound). A server-streamed `Attach` gives the hub a push channel to the agent without reverse-RPC plumbing.

### 2.3 `@crook/herdr`

An Effect client for Herdr's socket API. Private like everything else, but kept free of crook concepts anyway: it's the cleanest seam for testing the agent.

- `HerdrClient` service: `request(method, params)` typed by a `HerdrMethod` value (params + result schema), `snapshot`, and `subscribe(subscriptions)`. `subscribe` is scoped and resolves only once Herdr acks with `subscription_started`, yielding a `Stream<HerdrEvent>`; that ordering is the recovery contract, so the caller can `subscribe` then `snapshot` and miss nothing.
- Methods are added by the ticket that first calls them; today `ping`, `session.snapshot`, `pane.process_info`, `agent.prompt` (with its optional `wait`), `agent.send_keys`, `pane.rename`, `pane.close`, `pane.read`, and for launches `tab.create`, `workspace.create`, `worktree.create`, `pane.send_input`, `agent.start` and `agent.wait`. `agent_prompt_stalled` decodes to `HerdrPromptStalled`.
- A request keeps its connection's write side open until herdr answers. Ending the outgoing stream piped through `Socket.toChannelString` closes the write side, and herdr drops a request whose client hung up: `agent.wait` answered `client_disconnected` 105 ms and 125 ms after it was sent, and the client read `HerdrConnectionClosed`, so every launch on a real herdr 0.9.5 ended in `CommandDeliveryUnknown` with Claude running in its new pane (measured in a probe session, JC-111). Every connection the client opens now sends its one line followed by a stream that never ends, and `agent.wait` then waited out its full timeout. The function that opens the connection adds that tail itself, so neither `request` nor `subscribe` can leave it out.
- Screen reads (measured, herdr 0.9.5, shell panes in a named session): `pane.read { pane_id, source }` answers `pane_read` with `read { pane_id, workspace_id, tab_id, source, format, text, revision, truncated }`. `source` is `visible`, `recent`, `recent_unwrapped` or `detection`; crook reads `detection`, the text herdr's own blocked detection judges, which is how spike 80 captured its dialogs. `agent.send_keys` accepts the key names `down`, `up`, `enter` and `esc`, and `bogus` is `invalid_key`. To a pane whose agent was put there with `herdr pane report-agent` it answers `agent_not_ready` ("not an active named agent"), so a fake agent cannot stand in for a real one where keys must be delivered.
- Launching (measured on a herdr 0.9.5 probe session, 2 real Claudes started one after the other):
  - `tab.create { workspace_id, cwd, env }` and `workspace.create { cwd, env }` answer with the new root pane in 5–107 ms. `tab.create` needs an existing workspace (`workspace_not_found`). `env` is a string map laid over the server's environment for that pane, so a variable can be emptied but not unset; the emptied values reached the Claude started in the pane. A herdr server started from inside Claude Code hands Claude's variables to every pane (a probe session's shell carried `AI_AGENT`).
  - The new shell is not at its prompt at once: `agent.start` answered `agent_pane_busy` ("is not an available shell") for up to 27 ms after the pane was created, 1 and 2 times. It decodes to `HerdrPaneBusy`. herdr answers it while any child of the shell holds the pane's foreground, so under the laptop's zshrc, whose start-up runs tools one after another, the window ran to 274 ms (JC-124), which is why a launch waits for a printed ready mark instead.
  - `agent.start { name, kind, pane_id }` answers `agent_started` once it has typed `claude` into the shell, with `agent_status: unknown`, `launch_pending: true` and sequence 0. A prompt then is `agent_not_ready`. `agent.wait { target, until: [idle], timeout_ms }` answered `idle` with `interactive_ready` 3.9 s and 4.4 s after the start. Herdr's own readiness wait defaults to 30 s (`herdr agent start --help`). `name` must match `[a-z][a-z0-9_-]{0,31}` and be unique among live agents (`agent_name_taken`, a code read from the binary, not provoked).
  - `agent.prompt` with `wait: { until: [working, blocked] }` answered `working` after 604 ms; without it the answer came after 305 ms with the agent still `idle`. Herdr fails a prompt with `agent_prompt_stalled` when an accepted submission does not reach `working` or `blocked` within 5 s, and with `agent_blocked` before any input when the agent is already blocked (`herdr agent prompt --help`). A stalled prompt was typed.
  - `agent.start` types `claude` into the pane's shell, so the user's shell alias applies. On the laptop `claude` is a function that adds the user's own flags, `--disallowed-tools … AskUserQuestion` among them, and a Claude crook started ran with them (its command line, measured).
  - `pane.send_input { pane_id, text, keys }` answers `ok`. Sent 2 ms after the pane was created, while `agent.start` still answered `agent_pane_busy`, the text still reached the shell once it started, and `agent.start` was accepted 7 ms later (one run, no Claude).
  - A Claude started in herdr's default worktree path showed its folder-trust dialog ("Is this a project you created or one you trust?", `No, exit` selected): `agent.wait` until `idle` or `blocked` answered `blocked` after 3.9 s, and `agent.prompt` then answered `agent_blocked` (one run). `~/.claude.json` on the laptop trusts `/home/jliocsar/Projects`, not `/home/jliocsar`, and the Claudes started under `Projects` came up `idle`.
  - `worktree.create` with a `path` checks the branch out there, and finds the repository from a `cwd` in a subfolder of it (measured).
  - `worktree.create { cwd, branch }` creates the branch, checks it out, opens a workspace on it with a root shell pane and answers `worktree_created` with the workspace, tab, root pane and worktree. With no `path`, the checkout goes to `<worktrees.directory>/<repo name>/<branch with / as ->`, and `worktrees.directory` defaults to `~/.herdr/worktrees` (herdr's config template; measured: branch `probe/default-path` of a repo named `repo` landed in `~/.herdr/worktrees/repo/probe-default-path`). It takes no `env`, so its root pane carries the server's environment. The workspace it opens reads its `worktree.checkout_path` in the snapshot.
- Rename and close (measured on a herdr 0.9.5 probe session; the 0.9.1 binary carries the same method and param names, read from its strings, not run): `pane.rename { pane_id, label }` answers `pane_info` carrying the whole pane record, label set, and a `null` label clears it. It sends **no event** to any subscriber, lifecycle or otherwise, so nothing re-reads after it unless the caller asks. `agent.rename` is not a display name: it takes a handle matching `[a-z][a-z0-9_-]{0,31}` and rejects anything else with `invalid_agent_name`. `pane.close { pane_id }` answers `ok` and emits `pane_closed`; closing the only pane of a tab closes the tab too, with no `tab_closed`. Both answer `pane_not_found` for a pane herdr does not know.
- A pane label is what herdr's own views name a pane by, and plugins write it too: the auto-title plugin on the laptop names every pane after its work twice a second and leaves alone a pane renamed by hand, handing it back when the name is cleared (its README). So a pane's label can change with no event, and crook shows such a change at the next re-read.
- Agent input (measured, herdr 0.9.5): `agent.prompt { target, text }` answers `agent_prompted` after 302–403 ms (6 runs: it pastes, then sends Enter); `agent.send_keys { target, keys }` answers `ok` in 0.7–2.1 ms. Both take a pane id as `target` and reject a pane that hosts no agent with `agent_not_found`, so herdr enforces the same rule as `CommandPolicy`. An unknown key name is `invalid_key`; an empty key list is accepted and does nothing. A prompt to an agent already at an approval dialog is `agent_blocked`, rejected before any input is sent (herdr's own docs).
- Error codes crook acts on get their own tagged error: `events_lost` → `HerdrEventsLost`, `pane_not_found` → `HerdrPaneNotFound` (from any request or the subscribe itself), `agent_not_found` → `HerdrAgentNotFound`. Every other code stays `HerdrRequestRejected`.
- `state_change_seq` decodes to herdr's schema default of 0 when absent, so it is a plain `Int`.
- Schemas are hand-written from `herdr api schema --json` and decode only the fields crook reads: excess keys are ignored, so `layouts`, `tokens`, `state_labels` and `scroll` are left out. Optional or nullable fields decode to `Option`. Field names stay snake_case, as on the wire; mapping to `@crook/domain` happens in the agent, not here.
- Transport: NDJSON over a Unix socket via `@effect/platform-bun`'s `BunSocket.makeNet({ path })`. **One connection per request**: Herdr answers one request line and closes the connection, a second request on it gets nothing (measured, herdr 0.9.1). A subscription connection stays open. `events_lost` is expected as an error response carrying the subscribe request's id, then a close; that shape comes from herdr's schema and was never provoked (spike S6), so nothing relies on it beyond resubscribing.
- What ends a subscription (spike S6, herdr 0.9.5): a graceful stop, a `kill -9` and a live handoff all look the same, a clean EOF with no error line (`HerdrConnectionClosed`), so the subscriber cannot tell them apart. Reconnecting then fails with `ENOENT` after a stop (socket removed), `ECONNREFUSED` after a crash (socket file left behind; a regular file at the path behaves the same, which is how the test stands it in), and `ENOENT` for under 65 ms during a handoff; all three are `HerdrUnreachable`. A subscriber that stops reading is cut off with the same plain EOF once its socket buffer fills, not with `events_lost`. Events carry no sequence number and no heartbeat is sent, so nothing can be resumed: every reconnect resyncs from `session.snapshot`.
- Across a restart or a handoff, workspace, tab and pane ids survive and are never reused; `terminal_id` changes, `revision`, `state_change_seq` and `completion_seq` restart. A stop or crash kills every pane process, so restored panes come back as shells with no agents; a handoff keeps the processes, and each agent goes through about 3 s of not being known until herdr re-detects it, announced by a `pane.agent_status_changed` and no `pane_agent_detected`, with `completion_seq` lost. The spike's fake Claude read `unknown`/0 then `idle`/1; a real Claude reads `idle`/0, `unknown`/1, then its status at 2 (see 2.1).
- Close events are incomplete (spike S6): the shell exiting in a tab's only pane sends only `pane_exited`, and the tab is gone; `tab close` sends `tab_closed` and no `pane_closed` for its panes. The agent never cascades events itself: every event is a trigger to re-read the snapshot.
- Every subscribed event shape herdr 0.9.5 sent during the spike is kept as a fixture and decoded by the test suite. An event decodes to its name and an unread `data`: every event is only a trigger to re-read, so an event herdr adds, or a shape it changes, cannot end a subscription.
- Event wire shape (measured): a lifecycle event is `{"event":"pane_closed","data":{"type":"pane_closed",…}}` — snake_case, even though it is subscribed as `pane.closed`. The pane-scoped `pane.agent_status_changed` keeps the dotted name and carries no `data.type`.
- **Status changes need a pane-scoped subscription** (measured): `pane.agent_status_changed` requires a `pane_id`, and a lifecycle-only subscriber sees a `pane_updated` on the first detection of an agent but nothing for later working → blocked → idle moves. The agent subscribes per agent pane and resubscribes when the pane set changes (subscriptions are fixed per connection). An unknown `pane_id` rejects the whole subscribe with `pane_not_found`.
- Layers: `HerdrClient.layer` (socket path from `HERDR_SOCKET_PATH`, else `$HOME/.config/herdr/herdr.sock`), `HerdrClient.layerAt(path)`, `HerdrClient.layerTest({ responses, events, sent })`. Scripted responses are encoded lines run through the live decoder; a method given several lines answers them in order, then repeats the last, so a test can script a busy pane followed by a start; events come from a `Queue` whose failure becomes the stream's; the optional `sent` queue receives every request line as it would go over the socket, so a test can assert what was sent and how often.

### 2.4 `@crook/claude`

Built in JC-99, against the spike-82 captures and the laptop's own transcripts. Every module takes its roots or file as a value; nothing here reads herdr. Paths go through effect's `Path` service, so the services need `FileSystem` and `Path` from the entry point.

- `claudeRoots`: `CROOK_CLAUDE_ROOTS` (comma list) when set, else `$HOME/.claude`, plus `CLAUDE_CONFIG_DIR` when set, deduplicated. A root that is not an absolute path is `ClaudeRootNotAbsolute`, at startup: nothing expands `~` in a systemd unit or a plist, and a relative root would make the locator wait forever under the agent's cwd, since a missing `projects` folder is a normal state. A list that ends up naming no folder (`CROOK_CLAUDE_ROOTS=,` with no `CLAUDE_CONFIG_DIR`) is `ClaudeRootsEmpty`, at startup too, for the same reason: zero roots is a locator that waits forever and logs nothing. `HOME` is read only on the default branch.
- `FileWatch`: `watchReady(path)` (a ready signal, then the name of each changed entry, and each name of a burst once more after a short quiet, since Bun's `fs.watch` drops an event that lands right after the one it delivered) and `awaitPath(path)` (wait for a path, watching the nearest folder that exists), shared by the three services below.
- `TranscriptLocator`: `locate(session)` globs `<root>/projects/*/<session>.jsonl` over every root and never rebuilds the folder name from the cwd. `await(session)` watches each root's `projects` folder and its project folders until the file appears: Claude writes nothing before the first prompt (spike 82), so a session with no file is a normal state, not an error. `awaitSubagent` does the same for `<session>/subagents/agent-<id>.jsonl`. A session id is only looked up when it is letters, digits and dashes (`TranscriptSessionInvalid` otherwise), so a phone cannot walk a path out of the roots.
- `TranscriptTail`: `follow(file, from)` → `Stream<TranscriptChunk | TranscriptCaughtUp>`. `follow` sends `TranscriptCaughtUp` once, after its first read has reached the end of the file, at the offset after the last complete line: everything before it is the backlog, everything after it is live. A read is 64 KiB (effect's `FileSystem.stream` default chunk size). Only complete lines are parsed; the bytes after the last newline wait for the next read, because Claude's appends land in 4096-byte pieces and a reader can see half a line (spike 82). One chunk per read that completes at least one line, so a chunk is never empty of progress. `from` must be at most the file's size and right after a newline (`TranscriptOffsetBeyondEnd`, `TranscriptOffsetMidLine`); a file that shrinks under the tail is `TranscriptShrank`. `follow` re-reads on every watch event through a sliding buffer of one. `tailStart(file, bytes)` is the offset a tail watch starts at: the start of the line that holds the byte `bytes` from the end of the file (0 for a smaller file), found by reading back from there one 64 KiB window at a time until a newline, so one line longer than a window still lands on its own start.
- `SubagentRoster.watch(file)`: the session's `subagents/agent-<id>.meta.json` files as a sorted `Subagent` list, re-read on every change and emitted only when it differs. A meta without `agentType`, `description` or `spawnDepth`, keys spike 82 found in every meta, is skipped with a warning rather than given a made-up value. Workflow subagents (`subagents/workflows/<runId>/`, 2139 agent files against 828 flat ones in spike 82) are not listed and cannot be watched yet; the JC-101 subagent tree needs them.
- `SessionScans.follow(file)`: what the session's background work and notifications add up to so far, from one tail of the file from byte 0 that parses only the lines holding a marker. The roster, the background work and the running count all read it, keyed by file, so a session is read once however many watch it. A watcher that arrives later starts from the latest scan, so a phone unlocking reads nothing while the pane's Claude runs; the tail ends with its last watcher.
- `parseLine(bytes, offset)`: pure, one JSONL line's bytes → `readonly TranscriptMessage[]`; a blank line is no message. It takes bytes, not a decoded string, because a tear can split a multi-byte character and the decoder turns each dangling byte into U+FFFD, which re-encodes as 3 bytes: offsets counted on the string would land past the real ones.
  - Metadata Claude keeps for itself (24 entry types, the `stop_hook_summary` and `agents_killed` system subtypes, 45 attachment types, all seen in spike 82 or the laptop's transcripts) maps to nothing. Anything else unknown becomes `UnrecognizedEntry` (`system/<subtype>`, `attachment/<type>`, or the entry type), never dropped silently.
  - A human prompt queued while Claude works exists only as a `queued_command` attachment with `commandMode: "prompt"`, never as a user entry (0 of 262 on the laptop), so that attachment becomes `User { queued: true }`. One without `origin.kind: "human"` is skipped: it is not known who wrote it.
  - A line that is not JSON is salvaged. Spike 82 found 55 records in the history cut mid-string with the next record glued on, no newline between (cause not proven). The parser tries each `{"parentUuid"` or `{"type"` byte offset in order and emits `Malformed` for the bytes before the first one that parses, then the recovered entry at its own offset.
  - An image is stored twice per tool result (in the message and in `toolUseResult`); only the message copy is kept.
- Fixtures live in `packages/claude/test/fixtures`, copied from the spike-82 captures with the session's own ids.
- Ask derivation (built in JC-105, against the spike-80 captures), pure except `LastTurn`:
  - `HookPayload`: the five events crook listens to (`PreToolUse`, `PermissionRequest`, `PostToolUse`, `PostToolUseFailure`, `PostToolBatch`), decoded in their own snake_case.
  - `HookLedger`: per session, the calls that started and the pending permissions in arrival order. Claude queues dialogs, so a session can hold several (spike 80's codemode retry left two). A `PermissionRequest` carries no `tool_use_id`, so it claims the latest started call with the same tool name and an equal input that no other pending claimed (spike 80: the `PreToolUse` lands 32–55 ms before it). A `PreToolUse` that lands after its request attaches its id to the oldest unpaired pending with that name and input. Every `Post*` names its tool and input as well as its id, so a call whose id matched no pending still resolves the oldest unpaired one with the same name and input. A No or an Esc fires no hook at all, so the ledger cannot see a decline; the agent dismisses it (2.5).
  - `parseDialog(screen)` (`ScreenDialog`): the last `Esc to cancel` line ends the dialog and the `─` rule above its header starts it. `☐` marks a question, `· from the <x> plugin` the plugin, `k of M` after the header the dialog's place in Claude's queue, dashed rules split the body off, and `❯` marks the selected option. `keysToSelect(dialog, n)` is `down` or `up` from the selected option, then `enter`. `dialogFingerprint` hashes everything the dialog shows except the cursor and the queue's length: of `k of M` it keeps `k`, the dialog's place. Moving the cursor or queueing another dialog behind keeps it; a different command, file or option list changes it, and so does the next dialog of a queue, which can show the same command: spike 80's zombie and its retry both ran `echo cm6-bash > cm6-bash.txt`, and declining `1 of 2` left the same dialog as `2 of 2`.
  - `LastTurn.read(file)` reads the transcript from its end, 64 KiB first and doubling until the window holds the latest human prompt, never the whole file. `firstUnmatchedToolUse` is the first, not the last, tool use of that turn with no result, and nothing for a codemode run, whose inner call never reaches the transcript.
  - `deriveAsk` takes, in spike 80's order, the hook's pending permission, then the transcript's call, then the dialog on screen, then `UnknownAsk` with the raw screen. The pending permission is the one at the dialog's queue position counted from the newest end (`k of M` is pending number len − M + k), the newest when the dialog shows no counter: a declined permission leaves an older stale pending behind, never a newer one. A hook or transcript call the dialog contradicts is dropped, which falls through to the screen: a question against a permission, a question header the call does not carry, a header naming another tool, a Bash command the body does not show (compared with whitespace removed, since the dialog wraps it), or an Edit or Write path that is not the dialog's subject. `Notification(permission_prompt)` triggers nothing: it comes 6 s late and carries no tool data.
  - Ids: the `tool_use_id` when known, else `hook-<sequence>`, `screen-<dialog fingerprint>` or `blocked-<terminal>-<seq>`.
  - `editPatch(content, edit)` builds the hunks Claude will show from the file as it is on disk, with jsdiff's `structuredPatch` (the `diff` package, pinned) and 3 lines of context: Claude's `structuredPatch` leads with min(3, oldStart − 1) context lines in 199 of 217 hunks across 25 laptop transcripts. It equals Claude's recorded patch in 40 of 40 real edits replayed against their original files, where a hand-written line diff matched 28 of the same 40.
- Ask fixtures live in `packages/claude/test/fixtures/spike-80`, copied from the spike's captures, plus a capture of Claude 2.1.303's `Yes, and don’t ask again` dialog. The package exports them as `@crook/claude/fixtures/*`, and the agent's tests reach them through `import.meta.resolve` instead of keeping copies.
- The labels an `always` option starts with were read from the Claude 2.1.303 binary: `Yes, and always allow`, `Yes, and don't ask again` (with either apostrophe), `Yes, and allow `, `Yes, and remember this directory`, `Yes, and keep allowing`, `Yes, allow reading from` and `Yes, and switch to accept edits`. `Yes, and switch to auto mode` and `Yes, and use auto mode` change the session's mode rather than allow a tool, so they stay `other`.

MachineStateSync (built in JC-88, verified against a live herdr 0.9.1):

- The layer reads herdr once before it hands out the service, so the `SubscriptionRef` always holds a real `MachineState`; version 0 is that first read. A herdr that is down holds the layer up until it answers. That first read retries on the same backoff as the subscription.
- One loop, forked into the layer's scope: subscribe (lifecycle kinds that change `MachineState` plus one `pane.agent_status_changed` per agent pane), re-read once `subscription_started` arrives, then re-read on every event. A sliding buffer of one sits in front of the re-read, so a burst of events arriving during a read costs one more read, not one per event.
- A re-read that changes nothing keeps the version; a change bumps it by one. `statusChangedAt` is stamped by the agent at the read that first sees a status, since herdr carries no timestamp. A status herdr re-detects unchanged after a handoff keeps the stamp it had before (`beforeHandoff`), so a blocked agent that waited an hour still sorts as waiting an hour, and so does a `done` agent whose completion the handoff lost; the `unknown` row in between gets its own stamp.
- When a re-read shows a different set of agent panes, the subscription is closed and opened again with the new set. That is not a lost connection: the re-read after the new subscribe covers the gap.
- `pane_not_found` (a pane closed between the read and the subscribe) re-reads first so the next subscribe names live panes only. It is the one failure that is not a lost connection: herdr answered. A re-read that still lists the same agent panes would send the same rejected subscribe again, so that one goes down the lost path below and waits out the backoff instead (spike S6, rule 4: never retry the same pane set blindly).
- Every other end is one path, "herdr lost, state unknown" (spike S6: stop, crash, handoff and a slow reader all end as the same EOF, and `events_lost` joins them): resubscribe, re-read, replace. Herdr's sequences belong to one server lifetime, so nothing is resumed or compared across the gap.
- Backoff (built in JC-81): exponential from `HERDR_RECONNECT_BASE`, doubling, capped at `RECONNECT_CAP`, retried forever. The schedule (`reconnectBackoff`) and the health rule below (`stayedHealthy`) live in `@crook/protocol/LinkTiming`, beside `LINK_PING_INTERVAL` and `RECONNECT_CAP`: they are the one reconnect policy of herdr, the agent's HubLink and the phone's hub link, and only the base differs. The base is 100 ms: a herdr server cold-starts in 101–114 ms (measured), and the socket of a live handoff was missing for under 65 ms (one handoff probed with pings 21 ms apart; a reconnect 250 ms after the EOF succeeded on all 3 handoffs). The cap reuses `LINK_PING_INTERVAL` (5 s): a herdr that comes back is noticed no later than a hub that comes back. No jitter: jitter spreads many clients hitting one server, and each herdr server has exactly one agent.
- A connection is healthy once its first re-read after `subscription_started` succeeded and it then stayed up for one `RECONNECT_CAP`, the rule HubLink uses. A herdr that serves one snapshot and drops again (a crash loop under a supervisor) therefore keeps growing the backoff to the cap instead of being retried every 100 ms, and each cycle's lost and resync states reach the hub at most once per cap. The period is the cap itself, not a measured number: it is the longest the agent ever waits between attempts. When a healthy connection ends, the agent waits one base delay and reconnects with the backoff started over, so a handoff costs one 100 ms wait and nothing else. The wait comes first, not an immediate retry, because an immediate retry lands inside the handoff's missing-socket window. A resubscribe for a new pane set, or after an explained `pane_not_found`, is the same connection: it keeps the health it had, so a handoff right after a Claude starts or exits is still a healthy one.
- Reads carry a reply timeout of ten times the slowest measured (`HerdrTimedOut`; numbers in AGENTS.md), so a hung herdr fails a re-read instead of holding the state's lock. A re-read asked for by an invalidation that times out marks herdr lost and tells the following subscription, which sends it down the lost path below. An agent that cannot read herdr as it starts does not wait for it: it attaches with an empty state whose `herdr.lostAt` is set, and the first successful re-read replaces that state as a resync. The hub keeps the machine's seen marks and herdr version through a lost state, and the phone says "herdr lost" on an online machine.
- Losing herdr keeps the cached state and marks it, rather than dropping it: when a connection ends or an attempt fails before the connection was healthy, the state gets `herdr.lostAt` (once, with the version bumped, so the hub hears it). A handoff of a healthy connection never shows it, and one within a cap of connecting does, at once; a stop or crash shows it one base delay after the EOF. The first successful re-read after a loss clears it and carries a new `herdr.connection`, even when herdr shows exactly the herd it showed before, so the hub can tell a resync from a change. The id is a random safe integer from effect's `Random` (Math.random by default, so it differs across agent restarts); only inequality with the previous state's id is ever read.
- The snapshot's `panes` become `MachineState.panes`, and each agent row carries its `terminal_id`. Both feed the phone and the hub, never the agent's own logic.
- `ClaudeSessions` resolves a pane to its Claude session per S4: `agent_session` of kind `id` while a pid file names it, then the pid file (`pane.process_info` → the `claude` foreground process → its `CLAUDE_CONFIG_DIR` or `$HOME/.claude` from `/proc/<pid>/environ` → `sessions/<pid>.json`, kept only when its `procStart` matches `/proc/<pid>/stat` field 22). A missing file or closed pane is `None`. An unreadable or reshaped file, or a rejected or malformed `pane.process_info`, is logged as a warning and that one pane goes without a session; only transport failures abort the whole read. Herdr failures log at warning, except `HerdrUnreachable`, which repeats every interval while herdr is down and logs at debug. On the laptop 9 of 11 live agents resolve only through the pid file.
- `ClaudeSessionFiles` and `CheckoutHeads` (JC-148) watch what herdr says nothing about, and each wakes the following subscription's own read, so a change costs one re-read in the same sliding buffer as herdr's events. `ClaudeSessionFiles` watches `sessions` under each Claude root, reads a pid file when an event names it, and wakes only when what that file names changes: a session it did not, or a file gone. It also answers whether a pid file names a session, which is what tells `ClaudeSessions` that herdr's `agent_session` has gone stale. `CheckoutHeads` follows the folders of the state's agents, watches the git directory of each checkout they sit in (one watch however many folders share it), reads `HEAD` only when an event names it, and wakes when the branch it reads differs. A new watch wakes once, which closes the gap between the read that found the folder and the watch opening. It follows again whenever a branch changes as well as a folder, so a folder that became a checkout is watched from the first re-read that finds its branch; a `git init` itself wakes nothing, since nothing is watching there yet. A watch that fails, defects included, logs a warning and retries on the reconnect backoff, in its own fiber, so the state's reads never see it. Numbers in AGENTS.md.
- The machine id comes from `CROOK_MACHINE_ID`.
- `MachineState` carries herdr's server version from `session.snapshot`, not the hello: herdr can be updated or restarted under a running agent whose hub link never drops, and a version in the hello would go stale until the next reconnect. A herdr update bumps the state version like any other change.
- Branch (built in JC-98): herdr records carry the pane's `cwd` and `foreground_cwd` but no branch, and `worktree.list` reports branches per repository, not per pane. `GitBranches` finds the `.git` entry above the agent's cwd (a directory, or a linked worktree's `gitdir:` file), caches a found one per cwd (`effect/Cache`, so panes sharing a cwd walk the folders once), and reads `HEAD` on every re-read, so a checkout shows up with the next re-read, which `CheckoutHeads` asks for when `HEAD` moves. A miss is not cached: a folder that becomes a repository gets its branch at the next re-read, for a few `stat`s per re-read on panes outside git. A found directory whose `HEAD` has gone (a linked worktree removed and re-added under new metadata) is looked up once more on that read. A found directory that still has a `HEAD` is kept for the agent's lifetime: a folder resolved to an ancestor repository (a dotfiles repo in `$HOME`) that later gets its own `git init` or clone keeps showing the ancestor's branch until the agent restarts, a known limitation. A detached `HEAD`, a folder outside git and a pane without a cwd are `None`. An unreadable `.git` entry, `gitdir:` file or `HEAD` is logged as a warning and that pane goes without a branch, like an unreadable Claude session file.

HubLink (built in JC-89):

- One session per connection: build the RPC client, hold `Attach` open, and publish `MachineStateSync.changes` through a sliding buffer of one. `changes` replays the current value, so every new connection republishes the current state first, and a slow hub only ever gets the newest version.
- The session ends when `Attach` ends (`HubAttachEnded`), a call fails with `RpcClientError` (drop, refused or timed-out connect, ping timeout), the hub rejects a publish (`MachineIdMismatch`), or a call dies (`HubCallDefected`: the hub couldn't decode the payload, or its handler crashed). Defects are turned into that tagged error at the boundary, because `retry` and `forever` let a defect through and it would stop HubLink for good without a log line. Every end logs at warning and reconnects.
- A drop fails every in-flight call, because the socket protocol broadcasts the error before it consults its own retry, so `Attach` fails and the session ends. The protocol's retry is switched off (`retryPolicy: Schedule.recurs(0)`) so nothing redials inside a closing session; HubLink's schedule is the only one: exponential from `HUB_RECONNECT_BASE`, capped at `LINK_PING_INTERVAL`.
- A connection is healthy once the hub has accepted a publish and the link stayed up for a whole ping interval after it. When a healthy connection drops, HubLink reconnects at once and the backoff starts over. The clock starts at the first accepted publish, not at connect: a hub that takes the TCP connection but never finishes the upgrade fails each attempt after the socket's 10 s open timeout, and timing from connect would call that healthy and never back off (measured).
- `HUB_RECONNECT_BASE` (in `@crook/protocol`, with `hubReconnectSchedule` built on it from `reconnectBackoff`, since the phone's link reconnects the same way) is 77 ms, the slowest of 9 warm HTTPS requests from the laptop to an exe.dev VM's proxy (52–77 ms; the cold first one took 626 ms). `LINK_PING_INTERVAL` (in `@crook/protocol`, since the hub times agents out on it too) is effect's RpcClient default of 5 s, written out because the cap, the healthy period and the hub's silence timeout reuse it. S1 measured no proxy idle timeout within 900 s, so the ping exists to detect a dead hub, not to keep the proxy open.
- Config: `CROOK_HUB_URL` (the `ws`/`wss` URL of the hub's `/rpc/agent`) and `CROOK_HUB_TOKEN` (`Config.Redacted`), sent as `X-Exedev-Authorization: Bearer <token>`. `CROOK_MACHINE_LABEL` is optional; the hub labels a machine by its id without it.
- Every `Attach` sends the hello: the agent's own `package.json` version and the label. The socket's open timeout is written out as `LINK_OPEN_TIMEOUT` (effect's default of 10 s), because the hub's reconnect grace is built on it.

Commands (built in JC-103):

- `HubLink` runs the commands `Attach` delivers one at a time, in arrival order, and answers each with `CompleteCommand`. Input to one pane must keep its order (Stop, then a new prompt), and the slowest command measured is one prompt (403 ms), so nothing is gained by running them side by side. A `CompleteCommand` that fails ends the session like any other call. Launches are the exception, below.
- `CommandPolicy` admits input only to a pane that is in the current `MachineState.agents`, i.e. a pane herdr recognizes as hosting an agent, and returns that row. The agent reads its own state, never anything the hub claims. `CommandExecutor.layer` provides it, so the executor needs only `MachineStateSync` and `HerdrClient`.
- `CommandExecutor` remembers outcomes in an effect `Cache` keyed by `{ key, command }`, with effect's own structural equality: a retry is the same key carrying the same command. It remembers exactly the outcomes after which herdr may have acted, and forgets the rest:
  - remembered: `InputDelivered`, and `CommandDeliveryUnknown` (herdr closed the connection, answered something unreadable, or did not answer within `HERDR_DELIVERY_TIMEOUT` after the request went out). A retry replays them and never sends twice.
  - forgotten: `PaneNotAgent` (policy, or herdr's `pane_not_found` or `agent_not_found`: the agent exited between the state read and the send), `HerdrRefusedCommand` (any other herdr rejection, code and detail passed through), `HerdrUnavailable` (socket would not open). Nothing was sent, so a retry runs again.
- `COMMAND_REPLAY_CAPACITY` is 1024 keys, effect's `PersistedCache` default in-memory capacity, which is the same job: remember request outcomes by key in memory. When full the oldest key goes first. Nothing is persisted, so an agent restart forgets every key.
- `execute` is uninterruptible. A pending `Cache` lookup whose every caller is interrupted is itself interrupted and dropped from the cache (measured), so a session closing mid-prompt would otherwise let the retry send the prompt again.
- Because nothing can interrupt `execute`, the herdr delivery under it carries its own bound: `HERDR_DELIVERY_TIMEOUT`, 10 times the slowest measured prompt (403 ms), the same headroom `COMMAND_TIMEOUT` has. Without it a herdr that accepts the connection and never answers would hold the session forever: no reconnect, no state publishing, every later command stuck behind it. The bound plus the slowest measured warm round trip (77 ms) stays under `COMMAND_TIMEOUT`, so the hub hears `CommandDeliveryUnknown` before it gives up. An effect timeout still interrupts its losing side inside an uninterruptible region, since `raceFirst` forks both sides interruptible (read in its source, and probed).
- Herdr's `HerdrRequestInvalid` (crook built params herdr's schema cannot encode) is a defect: every `Command` that decodes encodes.

Launches (built in JC-111):

- `HubLink` forks each launch as it comes down Attach, ahead of the serial queue, instead of into it. A launch names no existing pane, so nothing orders it against input, and it can take as long as `LAUNCH_DELIVERY_TIMEOUT`, which would hold every Stop behind it. Forking it where it arrives, not where the queue reaches it, also starts its bound with the hub's: a launch queued behind a pane command's answer (up to `HERDR_DELIVERY_TIMEOUT`) would otherwise start its own clock that much after the hub's `LAUNCH_COMMAND_TIMEOUT` had. The pane commands wait in an unbounded buffer between the two, which holds at most what users sent while one answer was in flight. The launch goes into the link layer's scope in the fiber that reads Attach, and only the wait for its outcome is forked into the session: a launch forked from inside that waiter never started when the link dropped right after it arrived (measured). The launch runs in the link layer's own scope, not the session's: closing a scope waits for the fibers it interrupts, and `execute` is uninterruptible, so a launch in the session scope held the reconnect until it finished. The fiber that waits for it and answers `CompleteCommand` lives in the session and goes with it; the phone's retry under the same key gets the remembered outcome. Nothing caps how many launches run at once: each is one user's action.
- `AgentLauncher.launch` first resolves the folder (`/a/b/` and `/a/./b` are `/a/b`, the form herdr reports a cwd in), so a typed path finds the workspace already showing it and is remembered once among the recent places. It then checks that the folder is a directory: `FolderNotFound` when nothing is there, `FolderUnreadable` for any other failure to look (nothing sent either way). `StartAgent` then reads the snapshot and adds a tab to the workspace that already shows the folder (a worktree workspace checked out there, or a pane whose cwd is the folder), else creates a workspace. `CreateWorktree` finds the folder's checkout through `GitBranches` (`FolderNotCheckout` outside git), runs `worktree.create`, adds a tab at the new checkout, and closes herdr's own root pane of the new workspace once Claude is up, because `worktree.create` takes no `env`. That root pane is remembered as soon as herdr answers, and closed with Claude's pane when Claude does not start.
- The checkout goes beside the one it came from, `<checkout root>-<branch with / as ->`, which is the stand-in the decided Brief prototype used, instead of herdr's default `~/.herdr/worktrees`: Claude asked for folder trust there, so the task could never go in as the first message. Beside the checkout it inherits whatever folder the user trusted above it. A checkout whose parent is not trusted still stops at the dialog, and the launch ends in `TaskNotDelivered`, whose message names the trust prompt.
- Every pane crook opens gets `SCRUBBED_ENVIRONMENT`, the 12 variables a running Claude hands its children set to empty, and then `UNSET_CLAUDE_CHILD_VARIABLES` typed into its shell, which unsets them. Spike 80 measured that inherited `CLAUDE_CODE_*` variables removed AskUserQuestion and leaked the parent's bridge session, and that unsetting them brought AskUserQuestion back. Empty is not unset: Claude 2.1.303 reads `CLAUDE_CODE_CHILD_SESSION` and `CLAUDECODE` as `Boolean(value)`, where empty is false, but compares `CLAUDE_CODE_MESSAGING_SOCKET` against `undefined`, where empty still counts (read in its binary). After the typed `unset` the shell carried none of the 12 and only the user's three settings, and so did the Claude started in it (measured). The line starts with a space so a shell set to ignore such lines keeps it out of history. The 12 are 12 of the 15 `CLAUDE*` and `AI_AGENT` names found in a running Claude's environment; the other three are the user's own settings (one is in the login shell's environment, two are Claude settings toggles), which a new Claude should keep. The laptop's own herdr server carries none of the 15, so the scrub matters for a herdr started from inside Claude, which is what the probes did.
- The pane goes into `CreatedPanes` before Claude starts, so closing it never asks for confirmation, whether or not its task was delivered.
- Claude starts with `agent.start` under a crook-minted name, `crook-<n>` with the lowest `n` that no live agent uses and no launch in flight has reserved. The live names come from a snapshot read once the pane is open, and the name stays reserved until Claude is ready, by which time herdr lists the agent; two launches at once therefore never mint the same name, which herdr would refuse with `agent_name_taken`. Before that the setup line goes in with `pane.send_input` and ends in a `printf` of a ready mark split in two, so its echo never matches, and the launch waits for the mark with `pane.wait_for_output` for `SHELL_READY_TIMEOUT`, ten times the slowest measured 708 ms; a timed-out wait answers the code `timeout`. After the mark `agent_pane_busy` is retried every `SLOWEST_MEASURED_PROMPT_HOOKS` (58 ms, the longest the prompt hooks held the foreground) for up to ten times that: the multiplier is headroom, decided rather than measured, the same headroom `HERDR_DELIVERY_TIMEOUT` takes over the slowest prompt. Then `agent.wait` until `idle` or `blocked` for `AGENT_READY_TIMEOUT`, herdr's own 30 s default. A refusal or a timeout is `AgentNotStarted`, and the panes are closed and forgotten, so a failed launch leaves no shell behind.
- A task goes as `agent.prompt` waiting until `working` or `blocked`. A refusal is `TaskNotDelivered` and the pane stays: herdr refuses before typing anything, Claude is running, and the user can type the task in its chat. `agent_prompt_stalled` is not a refusal: herdr typed the task and Claude was slow to start on it, so the launch answers `AgentStarted` and the phone opens the chat, where the task shows. Resending it would run it twice.
- Replay: `AgentStarted`, `AgentNotStarted`, `TaskNotDelivered` and `CommandDeliveryUnknown` are remembered, so a retry never opens a second pane. A refusal before any pane was opened (`FolderNotFound`, `FolderUnreadable`, `FolderNotCheckout`, `HerdrRefusedCommand`, `HerdrUnavailable`, `HerdrAnswerUnreadable`) is forgotten. A lost connection once a pane exists is `CommandDeliveryUnknown`.
- Bounds: `LAUNCH_HERDR_WAIT` is `AGENT_READY_TIMEOUT` plus `PROMPT_START_WINDOW` (herdr's 5 s stall window). `LAUNCH_DELIVERY_TIMEOUT` is that plus `HERDR_DELIVERY_TIMEOUT`; the hub's `LAUNCH_COMMAND_TIMEOUT` is that plus `COMMAND_TIMEOUT`, and a test keeps the agent's bound plus one reconnect base under it.

Recent places (built in JC-111):

- Recent means the folders herdr's agent panes ran in, seen over time. Every re-read's agent rows go to `RecentPlaces.observe`, which merges every row's `cwd` at its `statusChangedAt` into a list at `CROOK_RECENT_PLACES_PATH` (default `$XDG_STATE_HOME/crook/recent-places.json`): one entry per folder at its latest use, newest first, at most `RECENT_PLACES_CAPACITY` (15: a product knob, not a measured value; the decided Brief design sets no row budget for the folder sheet). Folders that no longer exist are dropped before the capacity is applied, so a removed worktree frees its slot. The file is written whenever the list changes, through a temporary file renamed over it; since a use is stamped at the agent's status change, that is once per status change of any agent. An unreadable file starts the list empty, and the next change replaces it.
- A restart of the crook agent leaves the places' recency as it was. The first read cannot know when a running agent last changed, so its rows carry the read's own time, and keep it until the agent's status changes. `observe` takes that first-sight time and records a use stamped at it only for a folder the list does not hold yet; a stored folder moves up only on a status change crook saw. Folders first seen at the same restart tie, and the tie goes by folder name.
- Rejected sources: Claude's `~/.claude.json` lists 138 projects on the laptop, only 66 of which still exist, nested folders and `$HOME` included; a transcript folder's name encodes the cwd lossily, so the folder cannot be read back from it; herdr keeps nothing of a closed pane.
- `MachineStateSync` observes the places inside each re-read, from the agent rows that re-read produced, and publishes them in the same `MachineState` version as the agents. Checkouts and branches come from `GitBranches` at that point, so a place shows the branch checked out now. An earlier shape followed the published state in a separate loop, which cost a second version per status change and a second pass that changed nothing.

Rename and close (built in JC-112):

- `RenameAgent` is herdr's `pane.rename`, the name herdr's own views show, never `agent.rename` (a handle, see 2.3). `label: None` clears the name, which hands the pane back to whatever names it otherwise. The `PaneRenamed` receipt carries the label from herdr's `pane_info` reply, read the way the mapping reads it, so it states what herdr stored rather than what was asked. Because herdr sends no event for a rename, the executor asks `MachineStateSync.invalidate` for a re-read once the rename succeeded. The re-read is forked into the sync's scope rather than awaited, so the delivery bound against `COMMAND_TIMEOUT` still holds; a failed re-read is logged, and the next herdr event re-reads anyway.
- Close never touches a pane crook did not create unless the user confirmed it: `ClosePane { confirmed: false }` on a pane outside `CreatedPanes` fails with `PaneNotCreatedByCrook` before anything is sent, and the phone resends with `confirmed: true` under a new key once the user says so. The policy check stays on the agent, which reads its own record, never the hub's claim. Rename and close, like input, go only to panes in the current `MachineState.agents`.
- `CreatedPanes` is a JSON array of pane ids at `CROOK_CREATED_PANES_PATH` (default `$XDG_STATE_HOME/crook/created-panes.json`, `$HOME/.local/state` when unset, per the XDG base directory spec). Pane ids are the key because they survive herdr restarts, crashes and handoffs and are never reused within a session, while `terminal_id` changes on all three (spike-81). One set per machine suffices since crook drives one herdr session per machine (D11). Writes go to a temporary file renamed over the record, so a crash never leaves half a file; a missing or unreadable file starts the set empty, which only means more confirmations. An unreadable file is moved to the same path with `.unreadable` appended before anything can write over it, so the old record stays there to inspect (a later unreadable file replaces it). Any read failure but a missing file moves it, a passing one (`EIO`, `EMFILE`) included, so an intact record can end up set aside: leaving it in place would let the next change write over it with only the new pane, losing the record outright, while setting it aside costs extra confirmations and keeps every id recoverable; only when that move fails does the next change write over the file, and the warning says so. StartAgent (JC-111) is what calls `remember`; a successful close calls `forget`. `MachineStateSync` reads the set on every re-read and follows its changes, re-marking `createdByCrook` on the rows it already holds without asking herdr, under the same lock as a re-read, so a `remember` racing a re-read is never lost. Panes closed outside crook stay in the record, which is harmless while ids are not reused. The residual case: deleting a herdr session and starting a fresh one may restart its id counters (inferred, not measured), and a stale id could then match a pane crook did not create.

Audit log, agent side (built in JC-106):

- Every `CommandExecutor.execute` appends one line to `CROOK_AUDIT_LOG_PATH` (default `$XDG_STATE_HOME/crook/audit.jsonl`), replays and refusals included: when, the machine id (who, on this side: the hub vouched for the routed command, the machine is the one that ran it), the idempotency key (the same key the hub's audit records, which joins the two), the operation, its arguments after the policy, and the outcome. The file is written `0600` in a `0700` directory, the modes Claude Code gives its own transcripts (measured on 200 transcripts in `~/.claude/projects`).
- The line is written after the outcome, in `execute`'s uninterruptible region. A write that fails is logged at error and the command's answer stands: by then herdr has acted, and refusing to answer would only make the hub time out and the phone retry.
- Policy, one `auditPolicyConfig` in `@crook/domain/Audit` that agent and hub both read: `CROOK_AUDIT_ARGUMENT_LIMIT` characters per argument (default 200: decided, not measured; long enough to recognise a prompt by its opening, short enough that a pasted file does not land in the log). A string past it keeps that many characters and gains `…`; an array of strings (`keys`) spends one limit across its texts, and the last text it keeps gains the `…`, so a cut never reads as an extra key. `CROOK_AUDIT_REDACT` is a comma list, no spaces, of argument names written as `[redacted]`, or `none` to redact nothing (default none: the full prompt already sits in Claude's transcript on the same machine, at the same file mode). The names form a closed set: `pane`, `text`, `keys`, `label`, `confirmed`, `pinned`, `kind`, `folder`, `branch`. A launch's task is audited as `text`, so redacting `text` hides prompts and tasks alike. A misspelt or padded name fails at startup rather than silently logging what it meant to hide.
- No rotation and no retention limit yet.

Transcripts (built in JC-100):

- `TranscriptStreams.serve(link)` runs inside each HubLink session, beside `Attach` and the state publisher. It reads `TranscriptDemands` and keeps exactly the demanded watches running in a `FiberMap` keyed by watch id: a new id starts a fiber, a missing one interrupts it. A tail runs only while a phone watches it.
- A pane watch follows the pane's `claudeSession` in `MachineStateSync`. It emits `TranscriptOpened`, waits for the file, then merges the tail with the subagent roster. A session with no file yet has no backlog, so it sends `TranscriptCaughtUp` at once, before it waits; the tail sends another when the file appears. When the session changes (`/clear` makes a new session and file at once, spike 82), it switches: the new session opens from 0, and nothing more is read of the old file, since the phone starts its thread over on the open. `/compact` appends to the same file, so it needs nothing.
- A resume (`from`) in the current session continues at that offset. A resume naming another session opens the current one, and the phone starts its thread over: a thread shows one session, and the old file stays on the laptop for `/resume`.
- A subagent watch emits `TranscriptOpened` for the parent session, then follows `agent-<id>.jsonl` once it exists.
- A watch's `tail` is used wherever it would read a file from byte 0: a fresh pane watch, the session a `/clear` opens, a subagent file, and a restart the hub demands from the start of a session. It emits `omittedUpTo` first when it skips anything, so the hub's cursor and the phone's position move across the skipped bytes like across any chunk.
- A watch that resumes from a later offset reads on from there when what is left fits one read (1 MiB), and otherwise emits `omittedBetween` from its offset to a line start near the end and reads on from that, so a resume costs one message however wide the gap. A watch with no `tail` (Show earlier) reads everything. The phone keeps its rows above a Show earlier row at the hole, and the cache folds older holes into one row at the start of the file when it hands a view back.
- Every event goes out as `PublishTranscript` and waits for the hub's answer, so a slow phone slows its own watch, not the others. `TranscriptOutOfStep` restarts the watch from the position the hub expects. A library error (locate, tail, roster) is sent as `TranscriptWatchFailed` with its wire form, and the watch ends. A defect ends it the same way, as `TranscriptReadFailed` with the pretty cause, so the phone's stream fails visibly instead of hanging open. An `RpcClientError` ends it quietly, since the session is ending too.

Asks (built in JC-105):

- `crook-agent hook` is the command Claude runs for each hook event. It reads the payload from stdin, writes it to `CROOK_HOOK_SOCKET_PATH` (default `$XDG_STATE_HOME/crook/hook.sock`) and exits 0 with nothing on stdout whatever happens, so it can never answer a permission or hold Claude up. Delivery is bounded by `HOOK_DELIVERY_TIMEOUT_MILLIS`, ten times the slowest of 200 local deliveries (15.1 ms, a first and cold one; the medians of ten batches of 20 were 0.6–1.7 ms). Claude runs it three times per tool call, so it does not load the agent: `main.ts` sends a bare `hook` call to `HookForwarder`, which imports nothing, and reaches `Cli.ts` only through a dynamic import, which the release build's `--splitting` keeps in a chunk that a hook never parses. The forwarder's path default is held equal to the agent's by a test. `crook-agent hook --help` and any flag still go through the CLI.
- crook never edits a Claude settings file. `crook-agent hook-settings --command <cmd>` prints the hooks block, one `async: true` command hook per event, and the user merges it in. An `async` hook runs in the background and its decision is ignored (Claude's hook docs), so a slow or missing agent cannot hold a tool call up and the hook could not answer even by mistake. `--command` is required, so the snippet names whatever program the user runs the hook with. `install-service` prints the same block already filled in with the program it installed (below).
- `HookInbox` listens on that socket, decodes one payload per connection and folds it into the `HookLedger`. The server is half-open, so a connection closes only once its payload is in the ledger. The hook command does not wait for that: it closes its side once the socket has taken the payload, and the bytes stay readable, so the agent has the payload shortly after the command returns. Claude runs the hook as `async`, so nothing reads the ledger on the command's return. A payload it cannot decode is dropped at debug. If it cannot listen, it logs once at error and asks fall back to the transcript and the screen.
- `PendingAsks.askOf(info, session, mark)` runs in `MachineStateSync.read` for each agent, after its session. For a blocked agent it reads the screen (`pane.read`, `detection`) on every refresh, then the hook's pending permissions and, only when there are none, the transcript's last turn, then calls `deriveAsk`; an Edit gets its patch from the file. The result is cached per pane under (terminal, `stateChangeSeq`, the pending hook sequences, the dialog fingerprint), so an ask and its id stay put across the re-reads of one dialog, and the next dialog of a queue gets a new ask though herdr reports no new state. A refresh whose screen read failed is not cached, so the next one reads again.
- A declined permission fires no hook, so the ledger would keep it. The agent drops a session's pending permissions and started calls once it sees that agent `idle` or `done`, or no longer sees the session at all, keeping the records newer than the mark taken just before that snapshot, so a `PermissionRequest` that raced the snapshot survives. A `working` agent keeps them: the hook can arrive before herdr reports `blocked`.
- A new pending permission re-reads the herd (`PendingAsks.changes`), so the hook's fuller ask replaces a screen-only one without waiting for a herdr event. Its id changes with it, and an answer to the old id is `AskNotPending`.
- `CommandPolicy` admits `AnswerAsk` only while the row is `blocked` on that `AskId`. Every answer reads the dialog again first, and refuses with `AskNotPending` (and re-reads the herd) unless the screen still shows the dialog whose fingerprint the ask carries: an ask id alone does not tell one queued dialog from the next. `Approve`, `ApproveAlways` and `Choose` then press `down` or `up` from where the cursor is, then `enter`, through `agent.send_keys`, which is how spike 80 answered every dialog; `up` moves a Claude dialog's cursor (measured on Claude 2.1.303). `Approve` is the option labelled `Yes`, `ApproveAlways` one starting with an `always` label (2.4), `Choose` the option with that label, checked against the ask's choices before anything is read. `Decline` is `esc`, the measured route for both No and Esc.
- Answers to one pane run one at a time, under a per-pane lock, and the agent remembers the last ask it answered on each pane with the row's terminal and `stateChangeSeq`. A second key for the same ask, arriving before herdr reports the pane unblocked, is `AskNotPending` instead of a second `enter` on whatever dialog came next, and it re-reads the herd. A delivered answer re-reads the herd too unless herdr reports the pane unblocked within 380 ms, the slowest unblock measured after `esc`: Claude draws the next queued dialog without leaving `blocked`, so no herdr event would move the row onto it. How long Claude takes to draw that next dialog is not measured; a re-read that still finds the answered dialog keeps the answered ask, and the next tap on it re-reads again.
- A decline with a message is one action: `esc`, wait for the row to leave `blocked` (herdr refuses a prompt to a blocked agent with `agent_blocked`), then `agent.prompt`. The three steps share one `HERDR_DELIVERY_TIMEOUT` (4.03 s); the slowest measured run of them was 2.1 ms, 380 ms and 403 ms. herdr reported the pane unblocked 240–380 ms after `esc` (6 runs on Claude 2.1.303).
- "Always" leaves no trace crook can show later: Claude writes no record of the grant (none in 300 recent transcripts), so a note that a pane's tool was always-allowed needs the hub to keep it, and waits for the web lane.
- Agents crook starts (JC-111) need a scrubbed environment: spike 80's Claudes launched with a parent Claude's `CLAUDE_CODE_*` variables (`CLAUDE_CODE_CHILD_SESSION`, `CLAUDE_CODE_BRIDGE_SESSION_ID`, `CLAUDE_CODE_MESSAGING_SOCKET`) had no `AskUserQuestion` tool, so they could never raise a question card. Which variable does it was not isolated.
- A permission option the terminal wrapped is joined back into one label from its continuation lines: at a probe pane's width the always option of a Bash dialog broke after "from this" and its label lost the rest (measured, JC-105). Only labels change; the fingerprint and the keys still come from the screen's own lines.
- Not measured: dialogs with several questions or a multi-select one (refused as `QuestionnaireUnsupported`); what a large `Write` content adds to each published `MachineState`.

Service install (built in JC-114). The systemd claims are read from the man pages of the laptop's systemd 255; the launchd ones from Apple's `launchd.plist(5)` and `launchctl(1)`, untested on a Mac.

- `crook-agent run` launches `AgentDaemon.layer`, every live layer under `HubLink`, and is what the service runs. Against a named herdr 0.9.5 session holding one workspace it read the snapshot and went on to dial the hub, retrying on its backoff (measured). Against an empty one, whose `session.snapshot` carries no `focused_*` ids, it kept retrying the snapshot, logging that herdr closed the connection (measured; the cause is not traced).
- The service runs the program that ran `install-service`: `process.execPath` alone when `Bun.main` sits under `/$bunfs/`, which is a `bun build --compile` binary (measured: `execPath` is then the binary's own path, a path with a space included), else `process.execPath` and `Bun.main`. From a checkout that is the exact bun that ran the install, a versioned path under a version manager, so installing again after a bun upgrade is on the user.
- Settings come from the environment `install-service` runs in, through the agent's own `Config` definitions, the required three and every carried one (the audit argument limit and redaction list included), so a value the agent would refuse fails the install before anything is written (`ServiceSettingsUnreadable`). They go to `$XDG_CONFIG_HOME/crook/agent.env` (`~/.config` when that is unset or relative, through the one XDG fallback the state directory uses too), mode 0600 in a 0700 folder. It goes through the agent's one atomic writer, given a mode: any stale temporary is removed, the temporary is created fresh with that mode, chmodded past the umask, and renamed over, so the token is never in a file others can read and an install over a 0644 file leaves 0600. The unit and the plist only name the file; neither they nor the printed report hold the token.
- A user unit starts from the user manager's environment (`environment.d(5)`), not the shell's, so the variables the agent reads besides its required three are copied into the settings file when set at install time. One table pairs each carried variable, or the few read together such as the audit limit and redaction list, with the agent's own `Config` that reads them, so the copy and the check come from one entry and a new setting cannot join one without the other. A new agent setting joins that table, and a test fails until it does: it collects every quoted `CROOK_*`, `HERDR_*`, `XDG_*` and `CLAUDE_CONFIG_DIR` name in the sources of the agent and of the workspace members it depends on (the installer's own module aside), installs with each one set, and expects each in the settings file. The resolved `CROOK_HOOK_SOCKET_PATH` is always written, and the printed hook command sets it too, so Claude's hook and the service meet on one socket whatever `XDG_STATE_HOME` each of them sees.
- The unit, at `$XDG_CONFIG_HOME/systemd/user/crook-agent.service` (`systemd.unit(5)`, user unit search path). `install-service` takes `XDG_CONFIG_HOME` from the shell it runs in, and the user manager searches its own, so the two must agree: a value exported only from a shell's rc file leaves the unit where the manager does not look, and `systemctl --user enable` then fails, finding no such unit file (read, not run: the real user manager is off limits).
  - `Type=exec`: `systemd.service(5)` recommends it for long-running services, since a missing executable then fails the start job instead of passing unnoticed.
  - `ExecStart=` quotes every word, escaping `\` and `"`, `%` as `%%` (`systemd.unit(5)`, specifiers) and `$` as `$$` (`systemd.service(5)`, command lines). `EnvironmentFile=` (`systemd.exec(5)`) escapes `%` too.
  - `Restart=on-failure`: "the recommended choice for long-running services" (`systemd.service(5)`). Restarts are rate-limited by the defaults of `systemd-system.conf(5)`, five starts per 10 s with 100 ms between a stop and the next start, so a settings error leaves the unit failed after five quick tries instead of looping.
  - `SuccessExitStatus=130` (`systemd.service(5)`): `crook-agent run` handles SIGTERM itself, `BunRuntime.runMain` interrupts the program and `Runtime.defaultTeardown` exits 130 for an interrupt-only cause (measured: 130 after both SIGTERM and SIGINT, the CLI's `run` shape over `Layer.launch(Layer.empty)`). Only death by the signal itself counts as clean, so without it every `systemctl --user stop`, `restart` and logout would leave the unit `failed`.
  - `StandardOutput=journal` and `StandardError=journal` (`systemd.exec(5)`): journal is already the default (`DefaultStandardOutput=journal`), stated so a changed manager default cannot move the logs. `SyslogIdentifier=crook-agent`, since the tag is otherwise the process name, `bun` from a checkout. Logs: `journalctl --user -u crook-agent.service`.
  - `WantedBy=default.target`, "the main target of the user session" (`systemd.special(7)`).
  - Install is `systemctl --user daemon-reload`, `enable`, `restart`: `restart` starts a stopped unit and moves a running one onto the new definition (`systemctl(1)`). Uninstall is `disable --now`, remove the unit, `daemon-reload`, then the settings file goes too, so no token stays behind. A refused `disable --now` fails the uninstall before any file is removed. The stop runs only when the unit file exists; a settings file left without one is removed with a report saying nothing was running, so nothing was stopped. Neither touches Claude's settings, and the report says the hooks block stays.
  - A user manager stops at the last logout unless lingering is on (`loginctl(1)`, `enable-linger`). `install-service` prints that, and never runs it.
  - `systemd-analyze verify` (systemd 255) accepts the generated unit for a compiled program and for a checkout whose path holds a space and a `%`, with or without `--user`; a copy naming a missing binary and an unknown `Restart=` value fails it (all measured, on files under `tmp/`). With `SuccessExitStatus=130` added it still accepts the unit, and a copy with `SuccessExitStatus=notastatus` gets a `Failed to parse value` warning but exit 0, so verify does not gate on that directive (measured).
- The launchd agent, at `~/Library/LaunchAgents/crook-agent.plist` (per-user agents, `launchd.plist(5)`), label `crook-agent`:
  - launchd has no environment file, and `EnvironmentVariables` would put the token in the plist, so `ProgramArguments` is `/bin/sh -c 'set -a && . "$0" && exec "$@"' <settings file> <program…> run`. Each value is written double-quoted with `\`, `"`, `$` and the backtick escaped. A test reads a value holding all four, a `%`, a single quote and a newline back through that exact `sh` line (measured, `sh` only). That systemd's `EnvironmentFile=` unescapes the same four inside double quotes is read, not run (`systemd.exec(5)`, and a reviewer's reading of systemd's env-file parser): no route reads an environment file without a service manager, and the real user manager is off limits.
  - `RunAtLoad` and `KeepAlive` with `SuccessfulExit` false: start on load, restart unless it exited 0, the launchd form of `Restart=on-failure`. Restarts are spaced by launchd's `ThrottleInterval` default.
  - `StandardOutPath` and `StandardErrorPath` are `~/Library/Logs/crook-agent.log`, since launchd keeps no journal. Nothing rotates that file.
  - Stopping is `launchctl bootout gui/<uid>/crook-agent`. `launchctl(1)` documents only that a failure exits non-zero with a code `launchctl error` decodes, not which code means "not loaded", and none was measured on a Mac, so a refused `bootout` is followed by `launchctl print gui/<uid>/crook-agent`: when that succeeds the agent is still loaded and the refusal fails the command before any file changes; when it is refused too, nothing was loaded and the command goes on, and an uninstall reports that nothing was running rather than a stop. Install is that stop, `enable gui/<uid>/crook-agent` (clears a disabled override, which would otherwise refuse the load), `bootstrap gui/<uid> <plist>`. Uninstall is that stop and removing both files. The plist parses with Python's `plistlib` to the intended arguments (measured); `plutil` is not on the laptop.
- `ServiceManager.run(call)` spawns `systemctl --user …` or `launchctl …` through `ChildProcessSpawner`: a non-zero exit is `ServiceManagerRefused` with the exit code and stderr, a program that will not start is `ServiceManagerNotRun`. Its `layerTest` records the calls and answers them from a script; the installer's tests run against a temporary `HOME` and `XDG_CONFIG_HOME` and never reach a real service manager.

Service control and the Herdr plugin (built in JC-113). The systemd claims are read from `systemctl(1)` of the laptop's systemd 255 and the launchd ones from the same Apple pages as above; neither manager was run.

- `crook-agent status` prints the service's state, this program's version and what the running agent says about itself. The state is `systemctl --user show crook-agent.service --property=ActiveState,SubState,UnitFileState`, which `systemctl(1)` names the form meant for parsing, printing `name=value` lines and suppressing empty properties, so a missing one reads `unknown`. launchd's `print` output is not API (`launchctl(1)`), so on macOS the state is only whether `print` succeeds. A missing unit file or plist is "not installed" and asks no manager at all. A running agent older than the program is called out, since `install.sh` replaces the binary under a running service.
- `crook-agent start` is what the plugin's startup hook runs. It asks the status socket first: any answer, an unreadable one from another version included, means an agent runs, and nothing is started, so the hook never starts a second agent beside one run by hand. With no answer and no unit or plist it says so and exits 0; otherwise it is `systemctl --user start`, a no-op on an active unit, or on macOS `enable` and `bootstrap` only when `print` refuses, since a loaded agent with `KeepAlive` is already kept running. herdr starts startup hooks asynchronously and a failed one does not stop the server (herdr's plugin docs); against a fake agent the hook took 3 ms (measured).
- `crook-agent restart` is `systemctl --user restart`, or on macOS the install's own stop, `enable` and `bootstrap`. No unit or plist is `ServiceNotInstalled`, naming the connect action. `systemctl restart` returns once the new process is forked (`Type=simple`), well before it answers, so `restart` then asks the status socket again and again until an agent answers that is not the process that answered before the restart, and reports that process. It waits up to `AGENT_STARTUP_TIMEOUT`, 10 times the slowest start measured: `bun main.ts run` answered its first status request 211.7 to 249.5 ms after it was spawned (10 runs, herdr's socket missing). A later 193 runs read 181.8 to 257.7 ms, and it took up to 2656 ms beside 48 busy loops and 4947 ms beside 96, so a starved machine can outlast this wait. Past that it says that no new agent answered, and points at the logs.
- The status socket is `CROOK_STATUS_SOCKET_PATH` (default `$XDG_STATE_HOME/crook/status.sock`), always written into the settings file the way the hook socket is, so the service and a `status` run from Herdr meet on one path. It answers `RunningAgent`: version, process id, start time and `HubConnectionState`. The client writes one line and the agent answers once it has read it, then closes. An agent that answered on connect, before reading, made a Bun client's connect fail with `ECONNRESET` on most attempts (measured, Bun 1.4.3). `STATUS_ANSWER_TIMEOUT` is 10 times the slowest answer measured from a fresh process on a starved machine, 376.6 ms beside 96 busy loops on 16 threads (111 asks), so 3.766 s; past it the agent counts as not answering. The agent waits that same budget for the request. A missing socket or a dead agent's socket fails at once, so only an agent that took the connection and said nothing waits it out. `restart` polls every 21.269 ms, the slowest answer from a fresh process at rest (10 asks, 11.3 to 21.3 ms). The status socket and the hook socket share one listener, `LocalSocket`: make the state directory, remove a stale socket file, listen, fork the handler into the layer's scope.
- `HubConnectionStatus` is a layer of its own that HubLink writes and the status socket reads: online from the first publish the hub accepted on a connection, offline from the moment a session ended, with that end's message. Repeated failures keep the first offline time and replace the message. The status socket is merged beside HubLink, not built on it, so it answers while HubLink's layer still waits for herdr: `Layer.mergeAll` builds its layers concurrently (read in its source), and `crook-agent run` with herdr's socket missing answered `status` while it waited for herdr (measured).
- The plugin is plain POSIX `sh`, a manifest and one script at `packages/agent/plugin`, not a workspace member. It has no TypeScript to check, a machine running the compiled agent has no bun to run any, and every decision it needs (where the unit is, what systemd says, whether an agent answers) already lives in the agent. The script finds `crook-agent` at `$CROOK_INSTALL_DIR/crook-agent` (default `~/.local/bin`, where `install.sh` puts it) or on `PATH` and runs one of its commands. Its tests are the agent's: they run the script in a temporary tree with a fake agent, installer and herdr.
- It installs with `herdr plugin install jliocsar/crook/packages/agent/plugin`. herdr 0.9.5 makes a shallow clone of the whole repository, not a sparse one, from `https://github.com/jliocsar/crook.git`, and roots the plugin at the subdirectory: `plugin_root` is `<managed checkout>/packages/agent/plugin`, and `../../release/install.sh` exists beside it (measured, with git's `insteadOf` pointing that URL at a local bare copy of this branch, in an isolated herdr config). So the update action runs the `install.sh` of its own checkout, which is as trusted as the plugin, and downloads none. The repository is private; the laptop's git has no GitHub credentials (`git ls-remote` stopped at the username prompt, measured), so a machine needs some, such as `gh auth setup-git`, before the install can clone from GitHub itself.
- The manifest's version is the agent's, kept equal by a test, and `min_herdr_version` is 0.9.5, the only herdr it ran under.
- An action's command has no terminal and its output only reaches herdr's plugin log, so each action opens a popup pane of the plugin (`herdr plugin pane open --cwd <plugin root>`) that runs the script's interactive step. The pane's command is plain argv, `sh crook.sh <step>`, since `--cwd` already puts it in the plugin root (measured). Popups keep herdr's default size, which in a 140 by 45 client showed 55 columns by 22 rows (measured). A popup needs an active workspace: with none, opening one failed with `plugin_pane_open_failed`, "no active workspace" (measured).
  - Connect asks for the hub address, the token without echo, and the machine name (default `uname -n`), and runs `install-service` with the three in its environment only, so the token is never an argument. Typed into a popup in a real terminal, the token never reached the client's screen (measured); the tests, whose stdin is a pipe, only check that the script never prints it. It takes the agent endpoint the Add a machine sheet shows as it is. Without `crook-agent` it offers to run the checked installer first.
  - herdr gives every plugin command its session's `HERDR_SOCKET_PATH`, a named session's included (measured), and `install-service` carries that variable into the settings file. Connect runs `install-service` without it, so the service follows herdr's default socket, the one session SPEC §5.2 supports, whichever session the popup was opened in. Someone who wants a named session runs `install-service` with `HERDR_SOCKET_PATH` set themselves.
  - The `install-service` report, with the hooks block the user merges into Claude's settings, is about 70 lines, more than a popup shows. Connect writes it to `connect-report.txt` in `HERDR_PLUGIN_STATE_DIR` (`$XDG_STATE_HOME/herdr/plugins/crook`, measured), owner-only, pages it with `$PAGER` (default `less`), then names the file before the popup closes.
  - Status shows `crook-agent status` until a key other than `r` closes it. Restart runs `restart`, which waits for the new agent, then the same status screen.
  - Update asks for a version, empty meaning the latest release, runs the checked installer for the agent, then restarts the service, and closes with the restart's own success or failure. Nothing updates on its own. A release older than the plugin's `start`, `status` and `restart` commands answers them as any unknown subcommand, with the CLI's `USAGE` text and exit 1 (measured), so a failed agent command whose output carries `USAGE` is followed by a sentence saying what that means and pointing at the update action. Any other failure, such as a service not installed yet, is shown as the agent printed it.
- Checked in an isolated herdr 0.9.5 (`XDG_CONFIG_HOME` and `HOME` in the worktree, a named session, a fake agent): the plugin installed through `herdr plugin install` as above, the startup hook ran `crook-agent start` in the plugin's folder with `HERDR_PLUGIN_EVENT=startup`, the connect popup read the three answers, hid the token, handed them to `install-service` without `HERDR_SOCKET_PATH` and paged its report, and the restart popup showed the restart and then the status.

Server, identity and Herd (built in JC-90):

- Four GET routes, whose paths live in `@crook/protocol/HubRoutes` because the agent and the phone dial them too: `/health` (no headers needed), `/rpc/agent`, `/rpc/client`, and `/*` for the static PWA (below) with the SPA fallback (an extensionless path that accepts HTML gets `index.html`). The RPC handlers sit in `HttpRoutes` for now rather than in the two handler modules above.
- Every rejection is a tagged error that answers itself as a 403 carrying its `message` (`HttpServerRespondable`), so the router's access log records why.
- exe.dev sends the minter's email with every VM-token request, alongside the token's `ctx` (exe.dev docs, "What your server receives"). So the email alone can't tell the phone from an agent:
  - `/rpc/agent` wants the owner's email and a `ctx` with a machine id.
  - The phone routes want the owner's email and no `ctx` at all. Without that, a leaked agent token could watch the herd.
  - `/rpc/client` also wants `Origin` to equal `CROOK_HUB_ORIGIN`, which must be `https` (anything else fails at startup: a scheme-less value parses to origin `"null"`, which sandboxed pages send).
  - A token minted without a `ctx` looks exactly like a browser login. Only the owner can mint one, which is outside the threat model.
- Machine identity is read once, at the agent's upgrade, and each agent connection gets its own RPC server whose handlers close over that machine id. Handler `headers` can't be trusted for it: per-call headers override the upgrade's (AGENTS.md).
- The phone's login is bound the same way (JC-106): `admitPhoneSocket` returns the `X-ExeDev-Email` it admitted, and each phone connection gets its own `ClientApi` server whose handlers audit under that email. Today that email always equals `CROOK_OWNER_EMAIL`, since nobody else is admitted; it is recorded anyway so the log stays right if access ever widens.
- `Herd` holds one entry per machine: the number of live `Attach` streams, `lastSeenAt` and the last `MachineState`. Online means at least one `Attach` is open; counting lets a reconnect overlap the old connection without a false offline. Offline keeps the last state. `WatchHerd` is `SubscriptionRef.changes` behind a sliding buffer of one, so it emits the current view first and a slow phone only gets the newest. Machines are listed by id. Each phone's stream goes through `herdUpdates`, which compares a view with the one before it machine by machine and sends nothing when no visible entry changed.
- A dead agent socket that never closes is caught by Bun's `idleTimeout`, set to `SOCKET_SILENCE_TIMEOUT` (two `LINK_PING_INTERVAL`s, the same rule effect's RpcClient uses to call a hub dead). Bun's own pings are off (`sendPings: false`): through the proxy the proxy would answer them and keep a dead agent online. The agent's RPC pings are data frames, so a healthy agent stays up. A silent agent showed as dropped after 11.8–11.9 s against the 10 s timeout (5 runs, measured before JC-97, when a drop meant offline). Bun checks idle sockets on a 4 s tick: 8 sockets opened 0.5 s apart against a 10 s `idleTimeout` all closed at the same instant, after 8.5 to 12.0 s of silence (Bun 1.4.3), so a silent socket can drop up to one tick before the timeout, and the hub test bounds the silence from below by the timeout less that tick; a kill closes the socket and showed as dropped at once. Since JC-97 a dropped machine is `reconnecting` first and turns `offline` after `RECONNECT_GRACE`. The timeout is server-wide, so the PWA's client must ping within it too.
- Shutdown uses a `gracefulShutdownTimeout` of zero: sockets never finish on their own, so a grace period would only ever be waited out in full, and agents reconnect anyway.
- Config: `CROOK_HUB_PORT`, `CROOK_OWNER_EMAIL` (compared exactly), `CROOK_HUB_ORIGIN`, `CROOK_HUB_DATABASE_PATH`, the optional `CROOK_WEB_ROOT`, and the optional `CROOK_HUB_HARK_TOKEN` (redacted). `crook-hub --version` prints the version and starts nothing.

Static PWA (built in JC-115):

- With `CROOK_WEB_ROOT` set, the hub serves that directory: the dev path, pointed at what `bun run --filter @crook/web build` writes, and the way a compiled hub serves a build other than its own. Unset, a compiled hub serves the build it embeds. A hub run from source with it unset refuses to start (`WebRootUnset`), and so does one whose root holds no `index.html` (`WebBuildMissing`), rather than answering every page with a 404.
- The release build compiles the agent with `--splitting`, so the code behind the entry's dynamic import stays in a chunk inside the binary and a hook call never parses it (the smoke step runs a hook on the compiled binary).
- The release build embeds the web build with `bun build --compile --asset=packages/web/dist`. Bun keeps the directory under its own name, at `/$bunfs/root/dist`, and every bundled module's `import.meta.dirname` is `/$bunfs/root` (Bun 1.4.3, measured). The hub tells it is compiled from `Bun.embeddedFiles` not being empty. Vite's `outDir` and `assetsDir` are set from `@crook/web/build/WebBuild`, which the hub and the release build read as well, so the directory Vite writes, the one the release passes to `--asset`, and the one the hub serves are one name.
- Every page and asset carries `CONTENT_SECURITY_POLICY` as a header. A rejection (403) and an RPC upgrade are not documents and carry none.
- `SERVICE_WORKER_PATH` (`@crook/protocol/HubRoutes`, the path the phone registers) also gets `Cache-Control: no-cache`, so no HTTP cache between the browser's update check and the hub holds on to an old worker.
- No validators. An embedded file reports the epoch as its modification time (measured), so the static server's size-and-mtime `ETag` would match a same-sized file from another build and answer 304 with the old one; a rebuilt `index.html` keeps its length, since every hashed name it references does. The hub drops `ETag` and `Last-Modified` and ignores the conditional request headers, so every request is answered in full. The service worker's precache is what spares the phone the refetch.
- Files under `/assets/` get `Cache-Control: private, max-age=31536000, immutable`, the value RFC 8246 gives as its example. Vite names each of them after a hash of its content, so a new build never changes one in place, and with no validators left this is what keeps the browser from downloading them again. `private`, because every response is behind the owner's login.

Database (built in JC-97, shared by every later table):

- One SQLite file through `@effect/sql-sqlite-bun`, at `CROOK_HUB_DATABASE_PATH`. `Database.layer` builds the client and runs the migrations before anything reads, and `main.ts` provides it once; `Database.layerAt(":memory:")` is the test database.
- Every table comes from a numbered migration in the one migration record in `Database`, never from the module that reads it: migrations are history, and an `ALTER` belongs to no single repository. A later ticket appends the next number. So far: `1_machines`, `2_seen`, `3_seen_terminal`, `4_pins`, `5_audit`, `6_notifications`.
- Columns are snake_case. The client maps names camelCase ↔ snake_case both ways, so `sql.insert({ lastSeenAt })` writes `last_seen_at` and rows come back as `lastSeenAt`. Raw SQL text is not mapped.
- Each table has one schema, used both ways through `effect/sql/SqlSchema`: writes encode a record with it, reads decode rows with it. A row that does not decode is `StoredRowInvalid` and stops the hub at startup rather than serving a half-read herd. A record that does not encode is a defect: the record was built from that same schema.
- Memory stays authoritative while the hub runs; the database is what survives a restart. A write the agent link causes (attach, drop, publish) that fails is logged at error and the hub carries on from memory: failing it would drop every machine over a full disk. Each write of one link event is tried on its own: a publish whose machine save fails still deletes the seen marks it dropped, and a failed delete is logged too, leaving those marks in the table for a restart to load again. A write the phone asks for (forget, mark seen) runs before memory changes, and a failure returns `HubStorageFailed` with nothing changed.

Machine registry (built in JC-97):

- `machines` keeps id, label, last seen, forgotten, and the last agent and herdr versions, so after a hub restart every known machine is listed offline with its last seen and versions until its agent reconnects. The last state is not stored: an offline machine's agents are unknown. Last seen is written at each link event (attach, publish, drop), not while a connected machine stays quiet, so after an unclean hub stop (crash, OOM, reboot) a machine that never returns shows the time of its last link event, which can be older than its last connection.
- The label is the hello's label, else the id. It is rewritten on every attach.
- Connection is `online`, `reconnecting` or `offline`, and `connectionChangedAt` is when the machine last came online or last dropped ("Online for", "Reconnecting for"). A dropped machine is `reconnecting` for `RECONNECT_GRACE`, then `offline`. The grace is `LINK_OPEN_TIMEOUT` plus `LINK_PING_INTERVAL` (15 s): one dial can hang for the full open timeout against a hub that takes the TCP connection but never upgrades (measured, see HubLink), and HubLink never waits longer than one ping interval before the next dial. It is built from those two parts, not measured end to end against the exe.dev proxy. A machine loaded at startup is `offline`, with `connectionChangedAt` equal to its last seen.
- `ForgetMachine` hides an offline machine (online and reconnecting ones are refused); the row stays with `forgotten` set. The next `Attach` clears it, so a forgotten machine returns on its own.

Seen and needs-you (built in JC-98):

- The hub keeps, per machine and pane, the `terminal` and `state_change_seq` the user last saw. A pane is seen when both equal the pane's current ones. Equality, not "at least": herdr's sequence can restart lower, and a stale higher mark must not hide a new state.
- A mark is a `seenMarkOf(row)` (see 2.1): through a handoff the row keeps the identity of the state it continues, so a done agent the user had opened stays seen when herdr re-detects it, and one opened during the re-detection stays seen after it. `MarkSeen` records that identity, and the comparisons below are against it.
- A mark lives only while it equals the pane's current sequence: a publish that shows any other sequence for the pane, or no longer shows the pane, drops it, in memory and in the `seen` table, so a reused pane id starts unseen. Every kept mark therefore equals its pane's current sequence, and seen is just having a mark. Keeping a mark the pane has moved past would let a restarted sequence (pane ids such as `w1:p1` come back after a herdr restart, counting from 0) climb back to the old number and show a new state seen that nobody opened. The terminal closes the case equality alone left open (built in JC-81): herdr restarting while the hub hears nothing from that machine (agent disconnected, or the hub down), with the pane's first published sequence landing exactly on the old mark. Spike S6 measured on herdr 0.9.5 that `terminal_id` changes on every stop, crash and handoff while pane ids persist, so a mark from an earlier herdr lifetime never matches. A resync over the same herdr server keeps both, so it keeps the mark.
- Migration `3_seen_terminal` recreates `seen` with a `terminal` column and drops the marks recorded without one: they cannot be checked against a lifetime. The cost is one re-open of each done agent after that deploy.
- For JC-107, the notifier diffs consecutive publishes of one machine, and the domain carries what it needs to suppress the diffs that are not transitions; the diff itself is built with the notifier. A pair with `isResync(previous, next)`, or a `next` that `isHerdrLost`, is no transition at all: a resync diff spans a gap where herdr was not followed (after a restart every agent is gone, after a handoff each one reads `unknown` before it is re-detected), and diffing it against the cached state would fire "done" or "closed" for nothing that happened. A row that reads `unknown` is not yet known: it neither raises a notification nor withdraws one. The transition is judged when herdr re-detects the agent, against `beforeHandoff.status` when the row carries one, so a blocked agent re-detected blocked does not ask twice while one re-detected `done` after being `working` still counts. A `done` agent whose completion the handoff lost is published `done` again (see 2.1), so it neither withdraws a "Finished" nobody read nor leaves needs-you; its tab coming into view on the laptop publishes it `idle`, and that is a transition like herdr's own `done` to `idle`, which withdraws it. A row herdr never re-detects therefore changes nothing until herdr drops it from `agents`, which is a transition of its own ("Claude exited" or "This pane closed", by `panePresence`). The hub's first publish after its own restart has no previous state, so there is nothing to diff.
- `MarkSeen` records the pane's current sequence in the hub's last state for that machine; the phone sends it when a chat opens and again while a chat stays open on an agent that changes. Herdr focus is never called (D12): the hub has no herdr connection at all.
- Seen survives a hub restart (`seen` table). Lost marks would bring every opened done agent back as "needs you" after each deploy, inflate the tab badge, and (JC-107) notify again for what was already read. Marks are few and the table already exists, so the cost is one upsert per chat open.
- `HerdMachine.seen` lists the panes seen at their current sequence. `AgentPriority.orderAgents` sorts a machine's agents: blocked (longest waiting first), done and unseen (newest first), working, then idle and seen done, then unknown, keeping herdr's order inside the last three. Ties use `statusChangedAt`. `needsYouCount` counts blocked plus unseen done and is zero for an offline machine; `herdNeedsYouCount` sums the machines. Pinned agents come before all of them, ordered among themselves by the same tiers (the prototype's order); a pin never counts toward needs-you.

Pins (built in JC-112):

- Pinning is per user view, not a herdr concept, so it lives on the hub: the `pins` table keyed by `(machine, pane)`, loaded at startup, written before memory changes like every phone write. The pane id is the key because it survives herdr restarts and handoffs and is never reused (spike-81); `terminal_id` changes on every restart.
- A pin is not dropped when its pane leaves the published state. `HerdMachine.pinned` only lists pinned panes that are in the last state, so a pin whose agent exited shows again when an agent returns to that pane ("Start Claude in this pane" keeps its pin, as in the prototype). Since ids are never reused, a pin left behind by a closed pane never lands on another pane; it costs one row. The same residual as `CreatedPanes`: a deleted and recreated herdr session may reuse ids.

Audit log, hub side (built in JC-106):

- The `audit` table holds one row per audited phone action: when, the login (`actor`), the operation, the machine, the arguments after the policy as JSON, the idempotency key for commands, and the outcome with the failure's name. Two triggers abort any `UPDATE` or `DELETE` on it, so append-only is the database's rule, not just this code's habit.
- Audited: every `SendCommand` (the command's own operation and arguments, so `Prompt`, `SendKeys`, `RenameAgent`, `ClosePane`), `SetPinned` and `ForgetMachine`. Not audited: `MarkSeen`, sent at every chat open and again while a chat stays open on a changing agent. It changes no machine, only which badges show, and logging it would turn the audit log into a reading history that outnumbers every action in it. Watches change nothing.
- The row is written when the handler exits, interruptions included (`interrupted`: the phone dropped mid-command). A row that fails to write is logged at error and the phone's answer stands, like the agent's.
- Policy: the agent's, read from `CROOK_HUB_AUDIT_ARGUMENT_LIMIT` (default 200, the same decided default) and `CROOK_HUB_AUDIT_REDACT` (default `text`; `none` turns the default off, and an unknown name fails at startup). The hub redacts prompt text by default where the agent does not, because the hub keeps no transcript content anywhere else (D10): storing prompts in its database would put them on a machine that otherwise never holds them, while on the agent the full prompt already sits in Claude's transcript beside the log.
- No retention limit yet, as on the agent: the table grows by one row per audited action, and the triggers that make it append-only also block pruning. A later ticket that adds retention needs a migration that drops and recreates the `DELETE` trigger.

CommandRouter (built in JC-103):

- Each `Attach` registers an outbox with the router for as long as it lives, alongside `Herd.hold`. A command goes to the newest `Attach` of its machine, so while a reconnect overlaps a dying connection the command reaches the live one. No `Attach` at all is `MachineOffline`, before anything is sent, and so is an outbox that shut down between the lookup and the offer. The phone sends again once the machine shows online; nothing is queued for it.
- Herd's attachment count and the router's outboxes are two registries of one fact, acquired side by side in the same `Attach` merge, so for an instant after a connect or before a disconnect the herd may show a machine online that the router answers `MachineOffline` for.
- `send` gives the command the next `CommandId` (a counter: ids only have to be unique among the commands waiting in this process), parks a `Deferred` under it and awaits `CompleteCommand` for `commandTimeout(command)`, then fails with `CommandTimedOut`: `LAUNCH_COMMAND_TIMEOUT` for a launch (see Launches under 2.5), `COMMAND_TIMEOUT` for the rest. `COMMAND_TIMEOUT` lives in `@crook/protocol` beside `LINK_PING_INTERVAL`, because the agent's delivery bound is set against it. It is `LINK_PING_INTERVAL` (5 s), the link's own heartbeat: over 10 times the slowest measured prompt (403 ms) plus the slowest measured warm round trip to the proxy (77 ms).
- `complete` resolves the `Deferred` only if the answering connection is the machine the command was routed to; a late answer (after the timeout) or one from another machine is dropped with a debug log.
- A timed-out command may still run. The phone retries with the same key, and the agent answers with the first outcome instead of running it twice. Nothing tells the agent the hub gave up, so a command queued behind a slow one still runs late: a late `esc` can interrupt a turn started after it. Commands carry no deadline today.
- Commands are not persisted: a hub restart loses those in flight, and the phone sees them time out.
- A state counts only while no newer link has published. Each upgrade mints a link with a rising number and the router keeps which link published last, per machine. `CommandLink.publish` checks that and runs `Herd.publish` inside one update of that record, so a call from a connection the agent has left drops its state, even one waiting behind a newer link's write, and still replies with success. Numbers are in AGENTS.md.

Transcript relay (built in JC-100):

- One watch per `WatchTranscript` call, with an id from a counter. Two phones on the same pane are two watches and two tails: sharing one would need a cache to give the later phone what the first already got, and D10 says no cache. JC-100's "start a tail on the first subscriber, stop it on the last" is read as one subscriber per watch; this awaits the owner's sign-off.
- `WatchTranscript` asks the herd first, through the same membership rule `MarkSeen` uses (`Herd.requirePane`, `Herd.requireMachine`): the machine must be in the herd and, for a pane, the pane in its last published state (`MachineNotInHerd`, `PaneNotInHerd`). A subagent watch needs only the machine; the agent validates the session.
- The relay keeps, per watch, the machine, the source and a cursor (`TranscriptPosition`), never the messages. `demands(machine)` is the current set with each cursor, re-sent when the set of ids changes. An agent that reconnects therefore restarts every watch from where its phone stands, and the phone's stream survives the drop with no line repeated or lost.
- `publish` passes a chunk on only if it starts at the cursor (`continuesFrom`), else answers `TranscriptOutOfStep { expected }`. A `TranscriptOpened` for another session moves the cursor to its start. `TranscriptCaughtUp` moves nothing and is passed on, unless it names an offset past the cursor (`reachesPast`), which means a chunk never came and answers `TranscriptOutOfStep` too. Delivery per watch is serialised, so two overlapping agent connections cannot interleave.
- A publish counts only while its connection does. Each upgrade mints a link with a rising number, and a link stops counting once a later one asks for demands; a call on a link that stopped counting drops what is left of its updates and replies with success. Without it a frame delayed on a dead socket moved the cursor back to a finished session (measured through a real socket, see AGENTS.md).
- The phone's side of the inbox keeps its own position, of what it was handed, and lets through only `remainderAfter` it. The cursor moves after the inbox takes an event, as a second step, so a publish interrupted between the two (the agent's socket drops while the phone takes the event) leaves the cursor behind the phone; the reconnecting agent then resends lines the phone has, and this filter drops them. The same filter swallows the `TranscriptOpened` a restarted watch sends for the session the phone is already in, so a restart is invisible to the phone. The window is narrow in effect 4.0.5, which resumes a parked offerer synchronously inside the taker (`Queue` resumes it through `Effect.callback`, which calls `fiber.evaluate` in place), so no relay test can open it on demand; `remainderAfter` is tested on its own instead.
- The phone's inbox holds one event, so `PublishTranscript` only returns once the previous event left for the phone: backpressure runs from the phone to the agent's tail. `TranscriptWatchFailed` removes the watch and fails the phone's stream after what was already queued (effect's `Queue.fail` delivers buffered items first, probed). An update for a watch that is gone, or that belongs to another machine, is dropped with a debug log.
- Sizes, measured by draining 7 laptop transcripts (the 3 largest and 5 with images, 1468 chunks) and encoding each chunk as it goes on the wire: p50 12,527 B, p90 35,140 B, p99 421,705 B, max 732,560 B. The 95.5 MB transcript of a long orchestrator session became 910 chunks and 23.7 MB on the wire, drained in 612 ms on the laptop without the network. Bun's default WebSocket `maxPayloadLength` is 16 MiB (`bun-types`), over 20 times the largest chunk.
- `from: null` means byte 0, so a phone opening a long chat cold would download and parse all of it: that 23.7 MB, for the largest transcript on the laptop. The decision for JC-101, whose phone side is not built yet: the phone opens a chat with a `tail` of 512 KiB of the file. Measured over the 186 transcripts on the laptop (2026-10-21), the last 3 human prompts and everything after them took p50 216,851 B and p90 471,440 B of file (78 transcripts had 3 or more), and the last one alone p90 265,442 B, so a cold open would show the last three turns in 9 of 10 chats; half the transcripts (p50 230,569 B) are smaller than the tail and would arrive whole. "Show earlier messages" on the `Omitted` note is to watch the whole file again, as an explicit choice.
- Images travel inline as base64 in the chunk. Across 908 images on the laptop the base64 was p50 82,668 B, p99 518,524 B, max 671,428 B, and the most base64 in one line 727,536 B, all far under the payload limit, while a fetch RPC would need a hub-to-agent request path of its own. The phone decodes the base64 into a `Blob` and renders it from an object URL, which needs `img-src 'self' blob:` in the CSP (2.7): a `blob:` URL names only bytes the page made itself, with the media type it chose from the two the parser admits, where `data:` would let any inline image through. The CSP change lands with the first image the chat renders (JC-101), not before.

Notifications (built in JC-107):

- Hark's agent API, `POST /api/agent/notifications` and `POST /api/agent/notifications/:id/withdraw`, with `Authorization: Bearer` from `CROOK_HUB_HARK_TOKEN` (`Config.Redacted`; JC-107 needs the `notifications:send` scope, approvals add `interactions:create` and `interactions:read`, the Live Activity `activities:write`, per the OpenAPI document's `x-hark-scopes`). Without the variable the hub starts anyway: `HarkClient` logs one warning naming the variable, its `delivery` reads `noToken` (which the settings stream carries to the phone), every call fails with `HarkNotConfigured`, and the notifier never subscribes to the herd, so nothing queues up for a token that may never come.
- Copy, from `DESIGN.md` (Outside the app): the title is the agent's title (its label, else herdr's title, else the pane id), so each agent threads on its own in Hark; the body is a verb and where it runs, `Finished · laptop / crook` or `Has a question · desk / notes` (machine label, then workspace label). Every notification goes to one `crook` project, with no `url` (D16) and no `imageUrl` (Hark needs a public URL; the hub is private). Labels only: nothing Claude wrote. The title is cut to Hark's 80, never splitting a UTF-16 surrogate pair.
- What raises one: a publish whose agent row turns `done` (Finished) or `blocked` (Questions) from another known status, or shows that same status under another `seenMarkOf` identity, judged as in "Seen and needs-you" above: no raise across `isResync`, while `isHerdrLost`, from `unknown`, for a pane the previous state did not list, or for a row that still carries `beforeHandoff` (it reads `unknown` or the status it had before). The same-status case is the withdraw rule's mirror: herdr bumps the sequence on every detected change (2.1), so a new identity under the same status means a state in between that the hub never saw, because the agent publishes through a sliding buffer of one and a reconnect sends only the latest state. Without it, blocked at 5 then blocked at 7 would withdraw the first question for its moved identity and raise nothing for the second. A switch that is off sends nothing, and turning it off does not withdraw what is already out. Since JC-109 a `blocked` row whose `ask` is a `PermissionAsk` raises an approval instead (below); every other `blocked` is a question.
- What keeps one: a notification is out while its agent would still be needs-you for that same state. It is withdrawn when the pane is seen in crook (`MarkSeen`, or a publish whose `seen` lists it), when the row leaves `agents`, when its status is no longer the one it announced, or when its `seenMarkOf` identity moves on, and every notification of a machine goes when the machine is forgotten (`ForgetMachine`). The status check is what withdraws Finished on the laptop: herdr's `done` to `idle` on focus leaves `state_change_seq` unchanged (2.1). A row reading `unknown` keeps it, and so does a lost state, whose rows are the last ones read. A resync is judged like any other state: after a herdr stop or crash the agents are gone, and so is their needs-you.
- Shape: `Herd` publishes a `HerdChange` (`MachinePublished` with both states, the machine's label and the seen panes, `PaneSeen`, `MachineForgotten` once the forget is saved, and `MachineWentOffline` once a dropped machine's `RECONNECT_GRACE` runs out, which the notifier ignores because an offline machine keeps its notifications) on an unbounded `PubSub`; the notifier subscribes while its layer builds, so no publish is missed. It folds changes into the notifications it wants (`NotificationPlan.afterPublish`, `afterSeen`, `afterForgotten`, pure), and one fiber reconciles them with what Hark holds, one call at a time (`nextStep`: withdraw what is no longer wanted, then send what is). Because it compares the latest wants at each step, a Finished seen before its turn is never sent, and a burst costs at most one call per pane. The switches apply in one place, the step: a wanted notification whose switch is off becomes a `Drop`, which removes it from the wants only while it is still the one the step looked at, since the herd fiber may have replaced it meanwhile.
- A bug never stops the notifier. A defect while sending or withdrawing one notification is logged at error and that notification is given up on like a refusal, so one bad notification cannot block the rest; a defect anywhere else in a step is logged and the loop pauses `PAUSE_AFTER_HUB_BUG` before its next step, and a defect while folding a herd change is logged and that change skipped. That pause is `HARK_REQUEST_SPACING`, not the outage pause, because a bug is not Hark having trouble and has nothing to wait out: it only keeps a bug that repeats on every step from spinning, and at the request spacing such a loop runs no faster than a working one that calls Hark on every step. A send and the record of what it sent run uninterruptibly, so a hub shutting down mid-send still remembers a notification Hark created and can withdraw it after the restart.
- Rate: Hark allows 60 requests per minute per service on the free plan and counts an agent-token connection "like a service" (Hark docs, "Rate limits", and harkctl's "Send a notification"), over a rolling 60 s window. `HarkClient` admits one request at a time, in the order they asked, and starts each at least `HARK_REQUEST_SPACING` (60 s / 60 = 1 s) after the previous one finished, so no window holds more than 60 arrivals. A long poll (approvals, below) is the exception: it is admitted the same way but counts as finished once it is sent, since its answer can be 25 s away; holding the turn for it would stall every other call. Its starts are still 1 s apart, so a window still holds at most 60 starts, though arrivals can bunch by the network's jitter; a `429` then waits as below. The turn is handed to the oldest waiter on release, not left for whoever takes it next: Effect's `Semaphore` is not fair, and a loop that re-took it right after releasing starved another caller for 300 test-clock seconds (measured, see CLAUDE.md). A `429` with `Retry-After` waits what it says, then retries with the same `Idempotency-Key`; the header is read as seconds or as an HTTP date, rounded up to whole seconds and capped at the 60 s window, since a rolling 60-second window frees within one window and Hark itself sends `Retry-After: 60`. The cap keeps an absurd hint (`1e16`, a date in the year 9999) from sleeping the notifier for good or overflowing the schema's safe integer, and one the hub cannot read counts as no hint. A `429` without a hint is the monthly allowance, given up on like any refusal: logged at error, never retried, and forgotten once the state moves on. A `202` (Hark's "an identical request is still processing", documented for its webhook route) retries on the next turn. A withdrawal that fails for good is dropped; Hark answers 502 when no device took the removal, and that 502 is final.
- Outages: a transport failure, a request Hark does not answer within `HARK_REQUEST_TIMEOUT`, or any other 5xx is Hark having trouble (`HarkUnreachable`, `HarkServerFailed`), not a refusal: the notifier waits `HARK_OUTAGE_PAUSE` and retries with the same key, for sends and withdrawals alike, so an outage loses no notification and leaves no stale one on the lock screen. The pause is 60 s because the only wait Hark ever names is its `Retry-After: 60`; it documents no backoff for an outage. 400, 401, 403, 404 and 409 stay final.
- The timeout bounds the one request in flight, response body included, so a Hark that accepts the connection and never answers cannot hold the request permit and stall every later call and the phone's `SendTestNotification`. Without it Bun 1.4.3's own `fetch` gave up on a server that never answered after 360.4 s (measured, once). Twenty unauthenticated `POST /api/agent/notifications` from the laptop answered `401` in 137–471 ms, p50 about 140 ms (measured); an authenticated send also waits for Expo to take the push, which needs a token to measure. The 10 s is a choice made against those numbers, about twenty times the slowest round trip, and is to be re-measured once the token exists.
- The idempotency key is `crook/<machine>/<pane>/<terminal>/<state_change_seq>/<event>` (Hark keeps keys per service, up to 200 characters; a longer one goes without), so a retry never pushes twice.
- Sent notifications are kept in `hark_notifications` (one per pane) until withdrawn, and a restarted hub starts out wanting exactly those, so the first publish of each machine judges them: still done and unseen keeps one, anything else withdraws it. Notifications wanted but not yet sent are not kept. A stored notification of a machine no longer in the herd is not wanted at startup, and neither is one whose pane carries a stored seen mark with the same identity (a `MarkSeen` saved just before the hub stopped, its withdrawal not yet made), so the first step withdraws both. One whose state moved on while the hub was down can only be judged once that machine publishes: the hub does not store machine states. The switches live in `notification_prefs` (a missing row is on), loaded at startup and written before memory changes like every phone write, so every device shares them. All four default to on: setting the token is the opt-in.
- `SendTestNotification` sends title `crook` with a fixed labels-only body through the same client and spacing, and fails with `HarkReachedNoDevice` when Hark answers `accepted: 0`.

Approvals from the lock screen (built in JC-109):

- A `blocked` row whose `ask` is a `PermissionAsk` raises an `approvals` notification in the same plan as the others, one per pane, keyed like them plus the ask id (`crook/<machine>/<pane>/<terminal>/<state_change_seq>/approvals/<ask id>`). It is sent as `POST /api/agent/interactions` with `kind: approval`, `presentation: notification` (never `live_activity`, which would take the herd card's slot, `DESIGN.md` "Outside the app"), title the agent's title and prompt `Wants to run Bash · laptop / crook`: the tool name only, never the command (cut to the 2,000 characters a prompt allows, OpenAPI). It expires after 86,400 s, the longest Hark accepts (OpenAPI `expiresInSeconds` maximum; the docs' "30 to 86,400").
- The ask id is part of what an approval is. The agent replaces a screen-only ask with the hook's fuller one under a new id, and the next dialog of a queue gets a new ask under the same `state_change_seq` (2.5, `PendingAsks`), so a new id under the same state withdraws the old prompt and raises a new one: an Approve tapped for one dialog must never land on the next, which the `AnswerAsk` ask id would refuse anyway. Without a permission ask the row raises a question, as before; an ask that turns from one kind to the other under the same state is raised again as the new kind.
- An approval stays while the agent waits on that ask: seeing the pane in crook does not cancel it, because it is an action and not an alert (a question or Finished still goes on `MarkSeen`). It is cancelled (`POST /interactions/:id/cancel`) once the plan no longer wants it: answered in the app, declined on the laptop, the pane gone, the machine forgotten. Hark answers 404 to a cancel of a prompt that is no longer pending (docs, "Read and cancel"), which counts as done, so one already answered or closed on Hark's side is cancelled like any other: skipping that one request is not worth a set of closed prompts kept beside the plan, which a restarted hub would start empty anyway.
- Each approval out has one run (`ApprovalAnswers`, one per pane, owned by the notifier's scope), started when it is sent and for each one still wanted at startup, and told when it is withdrawn. It long-polls `GET /interactions/:id/wait?timeout=25` (25 s is the OpenAPI maximum), with a request timeout of 25 s plus `HARK_REQUEST_TIMEOUT`. A pending approval therefore spends about 60 / 25 = 2.4 of the 60 requests a minute while nobody answers it. `pending` polls again; `approved` routes `AnswerAsk { pane, ask, Approve }`, `denied` routes `Decline` with no message; `canceled`, `expired` and the other statuses close it without an answer. Outages and rate limits pause as for sends; a refusal ends the waiting, and the prompt is then only cancelled by the plan. Callbacks are not used: Hark needs a public URL and the hub is private (S3).
- The answer goes through the same `CommandRouter.send` as the phone's `SendCommand`, with the interaction id as `IdempotencyKey`, so a repeat lands on the agent's first outcome instead of typing twice. It waits for its machine rather than retrying on a timer. `CommandRouter.liveLink` says what the machine's newest attached link has published; the answer goes out over that link (`CommandRouter.sendOver`, which refuses it as offline if a newer link attached since) once that state shows the same pane, terminal, `state_change_seq` and ask id (`verdictOn`, the rule the plan judges by), whichever of the link's attach and first publish arrives first. A state that moved on ends the wait without sending; a state that cannot tell (herdr lost, a row reading `unknown`) keeps it. `MachineOffline` and `CommandTimedOut` hold the answer again, and it is never sent twice against the same published state, so a machine attached but not answering costs one send per publish instead of one every 15 s. It holds for `HARK_APPROVAL_EXPIRY` from Hark's `respondedAt`, the longest a prompt stays open, then gives up. Every other refusal (`AskNotPending` first) ends it. Each answer writes one audit row, actor `hark`, when its fate is known: delivered, refused, moved on (`AskNotPending`), aged out (`AnswerAgedOut`) or withdrawn while held; a hub stopping writes none, since a restart reads the answer from Hark again and resumes. A restart that finds a concluding row sends nothing; a row of `MachineOffline` or `CommandTimedOut` concludes nothing, which is what an older hub's retries left. Hark already shows that approval as answered, and the hub raises nothing in its place: an agent still waiting stays needs-you in crook and at its dialog on the laptop, where it can be answered, and one that moved on needs no answer. A send already out when the approval is withdrawn finishes, and its real outcome is what the row says.
- `harkctl permissions setup` is not used: it holds Claude in a hook and denies on timeout, which JC-109 rules out, and crook's own hook never answers (2.5). The agent stays at its dialog until an answer arrives from anywhere.

The herd Live Activity (built in JC-108):

- One activity for the whole herd (one per device, Hark docs "One per device"), under the fixed key `crook-herd` and always started with `replace: true`, so a start takes the slot from whatever holds it and the key from any earlier run. Title `crook`, accent `#EEEBE4`, no progress, symbol `warning`, `terminal` or `success` (`DESIGN.md` "Outside the app"). Status and detail follow the decided copy: `1 needs you · 2 working` with the agent that has waited longest (`Prototype the herd screen wants Bash · laptop`, or `has a question` without a permission ask), `3 working` with the one that started working last, and `All done` with no detail. Needs you is `blocked` here, as in the prototype's lock screen: a finished agent is not waiting on anyone. Status and detail are cut to Hark's 60 and 240 characters.
- It follows the same `HerdChange` stream as the notifier and the same signal for what is not a transition. A publish while `isHerdrLost` is not adopted, since its rows are the last ones read, but it starts a `RECONNECT_GRACE`: if herdr is still lost when that runs out, the machine's agents stop counting. A publish across `isResync` is adopted, as the notifier judges what it keeps by it: after a herdr stop or crash the agents are gone, and the card must not keep showing them. What a resync does not do is start a card: a herd that only a resync turned busy starts none until an agent turns `blocked` or `working` in a publish that is no resync, or the herd goes idle first. A resync also holds off the end for `RECONNECT_GRACE`, as the hub's own start does (below), so a herdr restart that empties the herd for a moment neither ends the card nor starts a new one, and one that empties it for good ends it a grace later. A row reading `unknown` keeps the agent as it was last known (a handoff's `beforeHandoff` status counts as known). A forgotten machine drops out. An offline one stops counting once `MachineWentOffline` arrives, which is already a grace after it dropped, so a closed laptop lid or a stopped VM ends the card on All done a grace later instead of leaving `1 working` up for as long as the machine stays away, restarted every 8 h with a sound. That is unlike its notifications, which stay: a notification is a one-off still to act on, while a card claiming a machine is working is false once nobody can see it work. The agents are kept, not dropped, so the machine's next publish is compared with what it last showed. That publish brings the machine back, and is treated like a resync for the start: if nothing else kept the herd busy, a returning machine whose agents are as they were starts no card (the user is usually at that machine), while one whose agent turned `blocked` or `working` meanwhile is a real transition and does.
- Steps (`ActivityPlan.nextActivityStep`, pure): start when the herd is busy (any agent `blocked` or `working`) and no activity is live, but never sooner than 60 s after the last start, because a start alerts and iOS drops fast successive ones (docs "Alerts and priority": "Space fresh starts out by a minute or so"); update (`PATCH`) only when the content changes; end on All done with `dismissAfterSeconds: 45`; end at once (`0`) when the switch is turned off. 45 s is the linger in Hark's own `activity end --dismiss-after 45s` example (docs "Drive a Live Activity"), and JC-108 picked it for `DESIGN.md` (Outside the app).
- It starts with `expiresInSeconds: 28800`, Hark's maximum and the 8 h cap, and `staleAfterSeconds: 28800` (`HARK_ACTIVITY_STALE_WINDOW`), a separate knob whose maximum is also 28,800 (docs "Expiry and staleness": stale defaults to 14,400 s, and only an update rolls it forward), because the card is only updated when its content changes and a herd that reads `1 working` for more than 4 h is not out of date. It restarts with the same key and `replace: true` one `HARK_RATE_WINDOW` (60 s, `ACTIVITY_RESTART_LEAD_OF_ONE_RATE_WINDOW`) before it expires: within one window the client admits every queued request, so the restart lands before the expiry unless Hark is down. An update Hark answers 404 or 409 (`already terminal`) means the card is gone, and the next step starts a new one, spaced like any start; an end answered 404 or 409 is done.
- `hark_live_activity` keeps one row: when the last start was and what the live card shows (`null` once ended), so a restarted hub neither starts a second card over a live one nor loses the spacing. Until `RECONNECT_GRACE` after the hub starts it does not end a live card: the herd is empty until each machine publishes again, and one that has not by then reads offline anyway. Updates during that window can show a partial herd.
- Outages and rate limits pause as for sends, and the step is then worked out again from the herd as it is by then. A start carries an `Idempotency-Key` (docs "Activity API": it works on all three write routes, a replay returns `idempotent: true`, a key reused with another payload is `409`): `crook/herd/<last start, or first>/<hash of the content>`, so a start Hark took whose answer was lost is replayed instead of alerting a second time within a minute, while a later start, or one with other content, gets another key. The hash is effect's 32-bit string hash; two contents colliding under the same last start would be refused once, logged, and tried again when the herd next settles. Nothing is recorded until Hark took the call: a start that failed is not counted as live, an update that failed leaves the old content as what the card shows, and an end that failed keeps the card, to be ended on the next step.
- A refused start, update or end is logged and not tried again until the herd settles, so a token without Pro (Hark answers 402) costs one refused start per busy spell rather than one per change.
- Without a token, or with the Live Activity switch off, nothing is sent. The switch is read from the notifier's settings stream, so it applies at once and is saved with the others.

- **A pushed screen is a child route** marked `staticData.pushed`, so its parent root list stays rendered (and inert) beneath it, and a deep link still has a parent to go back to.
- **The hub sends the CSP as a header** on every response, never a meta tag: a meta can't carry `frame-ancestors`, and Vite's dev server needs inline scripts. The policy is decided once, as `CONTENT_SECURITY_POLICY` in `@crook/web/csp/ContentSecurityPolicy`: everything `'self'`, with `default-src`, `base-uri`, `form-action` and `frame-ancestors` at `'none'`. Transcript images add `blob:` to `img-src` when the chat starts rendering them (2.6, JC-101). The hub imports that leaf rather than restating it, and sends it with every page and asset of the PWA (2.6). `vite preview` sends the same header, so a production build is checked under it locally.
- **A push hands over its opener.** The caller passes `openedFrom(element)` as the navigation's history state, with the element that was tapped (`Pressable` and `SwipeRow` give it to `onTap`). The pushed screen reads it once, when it mounts, and returns focus there when it unmounts, falling back to whatever had focus, then to the active tab. Document focus alone can't name the opener on an iPhone, where a tap doesn't focus a button. Openers are held by weak reference and never dropped, so a screen rebuilt by Back or Forward still finds its own, and a removed element can still be collected. One element always gets the same key, and every key carries the page load's `performance.timeOrigin`, because history state outlives a reload and a counter does not. So a second tap on a row whose push is still loading asks for the location the router is already on, and the router's `navigate` drops it: pushes go through `navigate` (`Link`, `useNavigate`), never `router.history.push`, which always pushes.
- **Every pushed entry gets its own screen.** The router remounts a route whenever its params change (`defaultRemountDeps`), so a chat opened from a chat slides in, takes focus and keeps its own opener. A screen slides in only when it arrives by a push (a higher history index than the resolved location's), so one rebuilt by Back or swapped in by a replace appears in place. Two entries with the same path share one screen: when Back lands on the earlier one, the screen comes back into use rather than staying inert. Back on a screen while a navigation is still pending skips the slide and leaves at once, which cancels a push that has not landed yet.
- **The service worker never calls `skipWaiting`.** A new shell takes over once every crook window has closed, so a running page never loads chunks from a build it didn't come from.
- **The service worker answers every same-origin navigation with the cached shell.** So log in and log out can't be a same-origin navigation to a proxy path: once the shell is cached, that navigation never reaches the exe.dev proxy. They go cross-origin to exe.dev, or to a path on the worker's `NavigationRoute` denylist. The proxy's paths are known now: exe.dev's docs put login at `/__exe.dev/login?redirect={path}` and logout at a POST to `/__exe.dev/logout`, so the whole `/__exe.dev/` prefix is denylisted, and "Log in with exe.dev" is a plain navigation there with the current path as `redirect`.
- **Settings reads the hub, never a copy (JC-110).** The switches and the account are streams the hub link follows over whichever connection is live (`whileDialed`): a drop ends nothing, and the next connection's `WatchNotificationSettings` takes over. Their atoms are kept alive once Settings has opened, so a second visit shows the last switches and email at once and the stream keeps them current (stale while revalidate); the cost is one quiet stream for the rest of the page's life. Before the first answer the switches and the email are skeletons shaped like their rows, never an off switch. A write and the test are one `Atom.fn` each (the write a family keyed by event), refused with `HubNotConnected` while the link is not live, like every other hub call.
- **Log out is a POST, never a navigation.** The service worker would answer a navigation with the shell, so the link `fetch`es `POST /__exe.dev/logout` (exe.dev's "Login with exe" docs), `redirect: 'manual'`, within the session check's timeout. An opaque redirect or a 2xx counts as done; anything else is `LogOutRefused`, a transport failure or the timeout `LogOutUnreachable`, and the phone stays logged in. Once done, the link stops following the page, which closes the socket, and only then clears the cached herd from IndexedDB and shows `LinkStatus.LoggedOut`: a herd update still in flight cannot write the herd back, the logged-out screen replaces everything, and a reopened crook has no herd to paint before its dial fails. A started logout runs to that point even if whoever asked for it goes away, since once the POST may have ended the cookie, a phone still showing a live herd would be wrong about its own state. What exe.dev answers that POST with, and whether a browser keeps the cookie removal of an opaque redirect, is unmeasured: measuring it needs the hub VM. Locally, after a mocked 200 the page held no IndexedDB keys and no connection to the hub (measured).
- **The Machines tab reads the herd it already has (JC-116).** Cards, counts, versions and the update pill are a pure layout over the same `HerdView` the Agents tab reads, through `herdAtom`, so the two tabs can't disagree; the machine screen's agents are the herd's own cards in `AgentPriority` order. The machine screen keeps the last model it showed once its machine leaves the herd, so a forgotten machine's screen slides out with its content instead of blanking.
- **Forget is one hub call per machine.** `forgetMachineAtom` is a family of `Atom.fn`s keyed by machine, so forgetting two offline machines in a row never interrupts the first call, and each screen waits for its own call's result. A refusal (`MachineStillConnected`, `MachineNotInHerd`, `HubStorageFailed`, or the link not live) is shown as the error's own sentence, UI state of the screen that asked; a hub action that fails with no typed error (a defect) shows one fixed sentence asking for a reload, the same for every action, and an interrupted one shows nothing; success needs no message, since the machine leaves the herd. The machine screen goes back once its forget succeeded.
- **Add a machine shows the agent endpoint on the page's own origin** (`agentSocketUrl`, `wss://<hub>/rpc/agent`), which is what the agent's `CROOK_HUB_URL` takes and what the plugin's "Connect to hub" action (JC-113) asks for, as it is. The install step is `herdr plugin install jliocsar/crook/packages/agent/plugin`.
- **A chat opened from the machine screen is the herd's chat route** (`/m/$machine/p/$pane`), so the herd sits beneath it during the slide and Back returns to the machine screen through history. The machine screen marks the push in its history state, and the chat reads that once, when it mounts, to name its Back "Back to <machine>" instead of "Back to Agents".
- **New agent is a layout over the herd plus one launch atom (JC-111).** What the screen shows (the summary, the chips, the empty cases) and the command it sends are pure functions of the `HerdView` and the screen's selection, so they are tested without a DOM. The selection (machine, folder, checkout or worktree branch) is React state: it starts as `mostRecentPlace` and is frozen the first time it shows on a live herd, so an agent changing status elsewhere never moves the chips under the user's thumb. Until the live herd arrives the default follows it, so a screen opened over the cached snapshot does not lock onto a place that is no longer the newest. A chosen folder is looked up again in each new herd, so its branch chip shows the branch checked out now, and a selection whose machine left the herd falls back to the default. A typed path must be absolute (the `FolderPath` schema) and loses its trailing separators, the form the agent stores a place in, so one that matches a published place takes that place's checkout. The worktree branch follows the task's first line, slugged (lowercase, runs of whitespace and `-` as one `-`, so it never starts with a dash), until the user types one; a typed one is sent cleaned (trimmed, whitespace runs as `-`), so it always passes `WorktreeBranch`. While the branch is empty the chip and the summary ask for a name and both starts stay disabled.
- **One `IdempotencyKey` per start, reused only where a retry is safe.** `launchAtom` is a `hubRuntime.fn` over `SendCommand` holding the action's state. It is one atom for the screen, not a family keyed by `IdempotencyKey` as 3.3 has it: the screen runs one launch at a time, with its controls disabled while one is pending, and holds the attempt (key, machine, command) itself, so a family would only add an atom per minted key that nothing else reads. The screen mints a key per start and resends under the same key only when the same command to the same machine failed without an outcome the agent remembers (a timeout, a lost or missing hub link, a refusal before any pane was opened). After `AgentNotStarted`, `TaskNotDelivered` or `CommandDeliveryUnknown` the agent replays the old outcome under the old key, so the next start mints a new one. Keys are 128 random bits from `crypto.getRandomValues`, in hex, because `crypto.randomUUID` exists only in secure contexts and a phone on a plain-http LAN address is not one.
- **"Done" is the pane in the herd, and the chat replaces the screen.** `AgentStarted` alone shows "Opening the chat…" with an "Open the chat" action, because the pane may never reach the herd (Claude exits at once, or the pane is closed from the terminal first) and no timer would be a measured one; once `hasStarted` finds the pane among that machine's agents, the screen navigates to the chat route with `replace`, carrying the opener key, so Back goes to Agents and focus returns to `+`. `TaskNotDelivered` leaves Claude running, so its error offers "Open the chat" the same way, and both start buttons stay disabled until the task or a chip changes: a second start would mint a new key and open a second Claude beside the one already waiting. The screen keeps its own 16px textarea, laid out as one row with its send button, and decides Enter with the chat composer's rule (below), from the same helper.
- **Pane actions are one sheet over one atom (JC-112).** `agentActionsAtom` holds one session per agent being acted on, which is the agent, where it was opened from, whether its sheet is on screen, and its last rename, close and pin attempt, and it takes intents. The sheet and the toast are mounted once, beside the shell where the root reads the connection: the shell itself reads no atom, so a test that renders it bare dials nothing. So a card, a machine's screen and the chat's `…` open it the same way: `useOpenAgentActions()(machine, pane, origin)`. Rename and Close are `SendCommand` (`RenameAgent`, `ClosePane`) through `sendCommandAtom`, a family keyed by `IdempotencyKey`, so each action has its own pending state and a later action never interrupts an earlier one's call. Pin is `SetPinned`, a hub write keyed by the pane, not a command. Progress is one `ActionProgress`, shared with the chat and the Ask dock: Idle, Sending, Sent (acked), Done (the herd shows it, `isReceiptShown`) or Failed with the error's own sentence and whether it asks for a confirmation; Done closes the sheet once nothing else in the session is still out or failed, so a pin that lands never hides a rename's failure. Dismissing the sheet while a close is out hides the session instead of dropping it, and so does opening another agent's sheet, so every close's outcome still runs, the chat's return to the herd included. A failed close shows its sheet again as soon as no other sheet is on screen; an outcome that ends a session clears it outright. Every send and every pin is kept alive in the registry: a dismissed sheet drops its session while a rename or pin is still out, and a call nothing subscribes to would be interrupted. The cost is one settled result per action for the life of the page. A close from the chat goes back through history and navigates to the herd only if Back did not land there, so the herd never sits twice in a row in history. It goes back only while the user is still on that agent's chat: a close dismissed in flight can land after the user opened another chat or went back to the herd, and then it shows only its toast. Focus moves to the tab only when no other sheet is on screen, so it never lands behind one.
- **A retry keeps its key unless the agent remembers how the command ended.** One predicate, `remembersOutcome`, decides it for launches, pane actions, the chat's commands and the Ask dock's answers alike, exhaustive over every `SendCommand` failure. The agent replays `AgentNotStarted`, `TaskNotDelivered`, `CommandDeliveryUnknown` and `DeclineMessageUndelivered` under the key they came back under, so a retry after one of them would only get the same failure back and mints a new key. After any other failure the agent either kept nothing or never heard of the command, so the same request sent again keeps its key, and a command that did run (a timeout, a lost hub link) is answered from the replay cache instead of running twice. A launch adds `LaunchAnsweredWithoutPane`, whose receipt the agent kept. A failure that carries no error mints a new key and shows the one sentence crook has for it, the same on every screen; an interruption reads as nothing having happened. Every new request mints a new key. `PaneNotCreatedByCrook` is not shown as a failure: it turns the Hold Button into "Hold to close anyway", and that hold sends `confirmed: true` under a new key, because it is a different command. A pane crook did not create asks for that confirmation before the first send, since the herd row carries `createdByCrook`. Once an attempt was confirmed, the sheet keeps asking for the rest of its session, so a confirmed close that timed out retries confirmed, under the same key.
- **Closed and exited are told apart once, when the agent goes.** The herd carries only panes that host an agent, so an ended agent is not drawn. If it ends while its sheet is open and no close is underway, `panePresence` on the machine's state says whether the pane is gone ("Pane closed") or still there without an agent ("Claude exited"), and the toast says so. A machine whose state is unknown says neither: after a hub restart the hub knows each machine from its record, with no state, until its agent publishes, so the sheet stays open on the last card it showed. A remembered card only ever stands in for the same agent. The toast is one atom with one line, replaced by the next.
- **The herd's order holds still while a swipe row is open or dragged.** The cards keep the order they had when the hold began; a card that arrived meanwhile goes last, and the live order returns when the row closes.
- **A transcript is one atom family keyed by pane or by subagent (JC-101).** The key says which file to watch and which herd decision makes it watchable, so the two kinds share every other atom (whole file, retries). Each runs `WatchTranscript` through `HubLink.watchTranscript`, which subscribes again on every live session and asks the atom where it stands each time: `from` is the position after the last chunk it applied, `tail` is 512 KiB on a first open (2.6) and none once "Show earlier messages" asked for the whole file. Every event passes through `remainderAfter` before it is applied, so a chunk the phone already holds is dropped and an overlapping one is cut to its new lines; that is the whole dedupe. A refused or failed watch shows as one row at the end of the thread with "Try again", and only while the pane is live: a closed, exited or offline pane has no watch worth reporting. A failed watch starts again on its own, from where the atom stands, when the herd next turns from not watchable to watchable (the pane an agent row on an online machine; a subagent's machine online), because the hub refuses a watch the moment its herd lacks the pane: after a hub restart the phone reconnects before the agent does, and the restored machine has no state yet (measured in the JC-101 probe: hub and agent stopped, hub started, the phone reconnected to an offline machine, the agent started, and the next prompt streamed into the open chat). The atom reads that decision as a derived boolean through `get.stream`, so a herd change re-runs nothing and only a flip wakes it. "Try again" restarts it the same way. A `TranscriptResumeRejected` (the file shrank, or the session moved) drops what the screen holds and opens again from the tail, at once; the screen keeps showing the old thread until the new one opens. The first event of a restarted watch clears the failure.
- **A chat shows its backlog at once, and opens again where it left off.** Each watch the phone starts awaits `TranscriptCaughtUp` when the machine's agent is at the hub's version or newer, which every agent that sends it is, since the two release together: the atom applies every event as it arrives but publishes nothing until the catch-up, so the thread goes from the skeleton to the whole backlog in one render, and every later event publishes as it lands. An agent behind the hub, or one whose version is unknown, may never send it, so its chats publish each event as before rather than sit on the skeleton. A failure publishes at once, with what arrived so far. Every published view is remembered in `TranscriptCache` and, once caught up, saved to IndexedDB (its own database, one entry per pane or subagent keyed by machine, source and Claude session), as are all unsaved views when the page is hidden and the watch's view when it ends; iOS ends a backgrounded PWA without telling it, so only what was saved survives a reopen. The next open of that chat, in the same run or a later one, shows the remembered view at once and resumes from its position, so only the delta crosses the wire, and the delta waits for its own catch-up behind the old thread rather than a skeleton. A pane keeps one entry, its latest session's; a save drops every entry whose session no agent of a known machine runs, and every entry of a machine the herd no longer has. "Show earlier messages" watches from byte 0 behind the remembered tail. The cache lives on the owner's device; D10's no-cache rule is about the hub.
- **Lines become chat items by one pure fold.** `chatItems(lines, { cwd, activity, subagents })` turns the transcript into prompts, Claude's text, tool calls (named like the terminal, one line of summary), a Subagent Tree per turn of `Agent` calls, the plan, notes, the compaction divider with its summary collapsed and the cleared divider. Meta entries and the local-command caveat are hidden. A subagent's status comes from its task notification, then the roster, then its tool result; a background run's tool result is only the launch, so its end time comes from the notification alone, and a finished run with no known end shows no duration rather than one that keeps growing. A turn's call with no result reads as stopped once a later turn started, or the agent is still.
- **Components never touch the transcript.** The chat screen reads the herd model, the transcript and the connection, folds them into rows and hands the thread plain rows; the thread virtualizes them with TanStack Virtual, follows the bottom while you are there and offers "Latest" once you scroll up. Its row gap and edge padding are the decided prototype's (`gap-3`, `pt-4` and a 16px bottom). The row estimate is the median rendered row of a real 24-row thread at 375×812 in the JC-101 probe (84px; quartiles 76 and 156, longest 3272 for a 900-word answer), and the overscan is one viewport of rows at that median (628px of thread, 8 rows). Items already there when the chat opens do not animate; later ones rise. The "Catching up" capsule rises 8px as it fades in, like the prototype's `Appear`.
- **Commands from the chat are pending actions keyed by their `IdempotencyKey` (3.3).** They send through the action sheet's `sendCommandAtom`, and `pendingActionAtom` folds its result and the herd into the sheet's `ActionProgress`: Idle, Sending, Sent (acked) and Done (`isReceiptShown`, the sheet's judge; a prompt whose pane has left the agents counts as shown, so an ack that lands before any herd has arrived stays Sent rather than being judged against no agents), Sent and Done carrying the receipt, or Failed with the error's own sentence, or the one sentence crook has for a failure that carries none. It is one type, generic over what an acknowledged action carries (a command's receipt, or the pinned flag for a pin), so the sheet, the chat and the Ask dock read one set of states and one fold. Prompt, Stop and restart are each one action with a current key and a spare: resending the same failed command reuses the current key unless the agent remembers how it ended (`remembersOutcome`, below), anything else moves to the spare and mints a new one. A sent prompt shows as a "Sent" bubble from the ack until the transcript holds as many more prompts than it did at the first send still unanswered as the phone has sent since: the count, not the text, so a resent "continue" still shows, and "Done" (the herd moving) does not end it before the line is tailed. That end is one way until the next send: "Show earlier messages" and a reopen from the tail stream the thread in again from fewer prompts, and the bubble must not come back while they do. A prompt typed on the laptop while the phone's is pending ends the bubble early; the phone's own then shows once it is tailed. A second prompt sent before the first is tailed keeps the bubble, now showing the second, until both are; a failed send that another send replaces is counted out. A slash command never comes back as a prompt, so it gets none and counts for none. A retry is the same command (`Equal.equals`, as New agent's `retryKey`). Stop is disabled while its Esc is in flight and for `STOP_SETTLE` after the ack, since two quick Escs are Claude Code's rewind gesture and the phone has no key strip to dismiss it. An Esc that interrupts moves the row and Stop becomes Send; one that does not (vim insert mode, below) never moves it, so Stop cannot wait for the herd and comes back once the window ends. The window is the slowest ack-to-herd-move the JC-101 probe measured at the phone (512 ms; the other four of five Escs took 297 to 357 ms; laptop, local hub, real Claude). A slower move leaves Stop pressable before it lands, so a second press there can still reach Claude as a double Esc.
- **Edge states come from the herd alone.** The screen model is live, away (machine offline), exited (the pane is still there, Claude is not), closed (the pane is gone) or not Claude (the pane never had an agent while the screen was open). It keeps the last row it saw, so the title, the folder and the transcript survive the end, and away keeps that row's status: an offline card dims the thread but does not rewrite a running tool as stopped or a subagent as failed. Only a closed or exited pane ends the turn, and the working row shows only while live. "Start Claude here again" starts one in that folder and replaces the chat with the new pane's, carrying the opener key and the machine-screen origin in the history state, so the new chat still names where Back goes (the route remounts on new params, so the screen's own state does not carry over). Nothing else moves the screen. A page loaded after Claude exited has no row to keep and shows the pane id. While the connection is stale (the cached herd painted at a cold start, or a link that is down), a pane the screen has never seen as an agent and the herd lacks is loading, not closed: the cache may predate the pane, so only a live herd can say it closed. Once the screen has seen the agent, a stale herd can still end it. The draft is the screen's React state, so it outlives the offline card that hides the composer.
- **The composer** is a 16px textarea. Enter sends from a hardware keyboard and adds a line on a coarse pointer, read from `(pointer: coarse)` at the keypress by one helper New agent's field shares; Ctrl+Enter and Cmd+Enter send on either, so a Bluetooth keyboard on a phone can send. Slash suggestions come from the agent: a pane's transcript watch sends a `SkillsChanged` event right after `TranscriptOpened`, carrying the `SkillCatalog`'s read of the folders Claude Code documents for the pane's folder (managed, personal, project skills and commands, enabled plugins); the web `TranscriptView` keeps the list across `/clear` and leaves it out of the cache, and the composer adds only the built-ins that work over a PTY. While blocked on an Ask, sending declines it with the text (`AnswerAsk` with `Decline`), one action the agent carries out as Esc and then the prompt, and the composer is held while an answer from the dock is out.
- **The Ask dock (JC-105) is the row's `ask` while it is blocked on a machine that is online, and nothing else.** It opens above the composer as a height collapse and closes when the row leaves `blocked`, since the row carries no ask otherwise; an offline machine's last known row can still be blocked, and then the ask is neither shown nor announced and its call stays in the thread, because the offline card replaces the dock and nothing could carry an answer; a new ask id remounts it, so a queued dialog never inherits the last one's state. A permission ask shows its tool, then the command, or an edit as the Diff View of the patch the agent read from the file, else of `old_string` and `new_string`, else the one-line summary; a write shows its content as a code block, since a diff against nothing would misread an overwrite. Yes and Always appear only when the dialog's options carry them, and No always, because Esc declines any dialog. A single question with one choice is a questionnaire whose choice goes as `Choose` and whose "Something else" is the composer's decline with a message, sent on the composer's action and not the dock's, because a `DeclineMessageUndelivered` can land after Esc has already unblocked the row and closed the dock, and only the composer outlives it; several questions, a multi-select one, or one whose kind the screen cannot tell are shown read-only with a plain decline, since the agent refuses those with `QuestionnaireUnsupported`; an unknown ask shows its raw screen with a plain decline. Each answer is the chat's pending-action pattern on its own action: one `AnswerAsk` under its own key, retried under the same key after a failure the agent does not remember, and `answerState` folds its `ActionProgress` into answering, answered, already answered (`AskNotPending`) or refused with the error's sentence. Only an answer in flight holds the dock's buttons and the composer. An answered ask keeps them, because the row can stay blocked on the same ask after a delivered answer (a queued dialog not drawn yet at the agent's re-read, or a key that did not land), and the agent answers the next tap, sent under a new key, with `AskNotPending` and a fresh read of the herd. The tool call an open ask is about (the ask id is its `tool_use_id` when the hook or the transcript named it) is left out of the thread so its diff does not show twice; notes are placed before it is hidden, so a note never moves when the call comes back. An acknowledged Always leaves a note after that call, or after the newest item when no call matches. The note is built from the ask in the third person ("Commands like this one allowed without asking again"), scoped to the session only when the option says so, and naming no file for an edit, because an edit dialog's Always switches Claude to accepting edits, which its label says covers every file edit and not the one asked about; all that, since the option's own label is Claude's first-person answer with a key hint and a path; the caption under the buttons is that label without its "Yes, and" and its key hint. The note lives in a kept-alive atom per agent, so it survives leaving the chat but not a reload, since nothing on the machine records the grant. The dock and the composer share the space above the keyboard: the thread gives way first, then the ask scrolls inside what is left, so neither the composer nor the answers sit behind the keyboard (checked with the visual viewport shrunk by 300 and 420 px at 375×812, on an edit and a questionnaire). A message that did not reach Claude goes back into the composer when the field is empty, so text typed into the dock survives the dock, and sending it again once the row has left `blocked` is a plain prompt, as that refusal's sentence asks. A polite status line announces each ask's title, and a dock that closes while it held keyboard focus hands it to the composer instead of dropping it on the page.
- **A close from the chat's sheet never shows the ended card.** The herd update that makes the close Done is the one that ends the chat, so both land in the same render and the card showed while the navigation back ran (measured by a test that watched the DOM). The chat latches the close it started for the rest of its life and shows neither the card nor the dock once it is done.
- **A message's markdown keeps its DOM while the clock ticks.** The chat re-renders every second for its elapsed times, and react-markdown takes its component map as element types, so a map built in render remounted every link and code block each second: a sideways-scrolled code block jumped back, a selection or a focused link was lost. The map is built once per code renderer and the message component is memoized on its text.
- **Code is highlighted by Shiki** (core, JS regex engine, the grammars named in one module), loaded by dynamic import into one kept-alive atom. Code renders plain until it arrives, and so does any block longer than 300 lines: tokenizing TypeScript with the JS engine took 41ms for 300 lines and 55ms for 400 (laptop, Bun, median of five), and a main-thread task over 50ms is a long task. Read, Write and Edit output shows its first 300 lines behind "Show N more lines", and Read's `cat -n` numbering is dropped before display and copy. A phone is slower than the laptop by an amount not measured yet. Its hast is walked into React elements, never `innerHTML`, with `defaultColor: false`, so each token carries both themes as custom properties and the stylesheet picks one by `prefers-color-scheme`.
- **Transcript images become object URLs** (`blob:`, which the CSP admits for `img-src`), made from the base64 when a thumbnail mounts and revoked when it unmounts. The full-screen viewer is one per screen, above the thread, and makes its own URL for as long as it is open: the thread unmounts a row once it leaves the overscan, and the live tail does that within seconds, so a viewer owned by its row closed under the user. The viewer's zoom, double-tap and swipe-down numbers are the decided prototype's, and its swipe-down shares the sheet's dismiss distance and speed, which the prototype also wrote twice with the same values.
- **A row's open and expanded toggles outlive the row's unmount.** The tool call's panel, "Show N more lines" and the compaction summary keep their state in the thread, keyed by the row's key and the toggle's name, so scrolling away and back or the live tail passing does not fold them again. A row holds at most one of each today; two of the same kind in one row would share one state.
- **The status word in the chat header is a polite live region**, as the decided prototype's header announces the agent's fate: a screen reader hears the agent move to working, needs you, done or the pane's end without re-reading recycled thread rows. The thread itself is no live region, since the virtualizer mounts rows again as they scroll back in.
- **Stop is one Esc, and Claude does not always take it as an interrupt (measured in the JC-101 probe).** With Claude's `editorMode: "vim"` and its input in insert mode, Esc only switched the input to normal mode: the turn ran to the end, and the hub had audited the `SendKeys` as succeeded. In normal mode the same Esc interrupted. An interrupted turn puts its prompt back in Claude's input, and the next `Prompt` was typed after it, so Claude received both texts as one message. Both belong to the agent's command delivery, which knows neither the editor mode nor what the input holds; the chat shows what Claude received.
- Tests run on vitest with happy-dom for components and node for pure modules.

## 3. Patterns

### 3.1 State is a value, events are triggers

Herdr says its events invalidate and its reads are authoritative. So:

- The agent keeps one `MachineState` in a `SubscriptionRef`. A Herdr event (or a reconnect) triggers a re-read; the result **replaces** the value.
- The agent publishes the whole `MachineState` with a monotonically increasing `version` whenever it changes (coalesced so a burst of events is one publish).
- The hub keeps the latest value per machine. It sends a phone the whole `HerdView` once, then each machine whose entry changed, whole (`HerdUpdate`, §2.2). The phone replaces that machine; nothing patches inside one.
- No event log, no replay, no ordering bugs.
- Sizes, measured (JC-94) by encoding with the codec the sockets use (`Schema.toCodecJson` of the RPC schema, framed by `RpcSerialization.ndjson`): a machine with one tab per agent holding the agent's pane and a shell pane, every agent with a title, label, branch and Claude session, and `RECENT_PLACES_CAPACITY` (15) places. The counters carry the five digits the fixtures use for a herdr `state_change_seq`, and the herdr connection id the widest value `Random.nextInt`, which mints it, can draw. The counts are the NDJSON message alone; WebSocket framing and, behind the exe.dev proxy, TLS records come on top. A whole `MachineState` publish is 3,157 B for 1 agent, 8,616 B for 10 and 20,906 B for 30: about 612 B per agent over 2,545 B of places and machine fields. Those publish figures, and the two with an ask below, come from a one-off probe over the wire size test's fixture, deleted once read; the test itself holds only the two sides of the line, so a schema change is checked against the decision, not against these numbers. An ask adds its tool input on top. Across 40 of the laptop's 526 transcripts, sampled at random, Bash commands were p90 1,360 B and Write contents p90 16,043 B (p99 55,698 B), which put a 10-agent publish with one such ask at 10,149 B and 24,883 B. A phone's whole herd of three machines of 10 agents is 26,391 B.
- Decision: per-machine replacement on the hub → phone leg, with one TCP initial window as the line, 14,600 B: RFC 6928 sets it to `min(10*MSS, max(2*MSS, 14600))`, and Linux has used it by default since 2.6.39. A connection idle for longer than its retransmission timeout starts over from that window (RFC 5681 §4.1; `tcp_slow_start_after_idle` is 1 on the laptop, measured), and a herd push is a message after a quiet stretch, so one past the window costs another round trip. The window that counts is the exe.dev proxy's, which sends to the phone; it is unmeasured, and the RFC default is the assumption. The whole herd crosses the line at two machines of 10 agents (17,631 B). One machine's replacement stays under it through 19 agents without an ask (14,374 B; 20 agents is 14,990 B). The wire size test builds that machine and holds both sides of the decision: a 10-agent machine's replacement under the line, and the whole herd of two of them over it.
- The agent → hub leg stays whole: it carries one machine already, so per-machine replacement cannot shrink it, and it is a server-to-server link. Diffs inside a machine stay last: what one entry still outgrows is a large ask, and per-row diffs would not shrink the ask either.
- Not done: permessage-deflate. The same encodings deflate to 1 to 2 KB, but those fixtures repeat strings far more than a real herd does, and whether the exe.dev proxy passes `Sec-WebSocket-Extensions` through is unmeasured.

### 3.2 Append-only streams with offsets

Transcripts are append-only files, so they travel as `TranscriptChunk { session, offset, nextOffset, messages }`. The phone remembers the `{ session, nextOffset }` of the last chunk; reconnect = `WatchTranscript { from }`. Nothing is cached in the hub (D10): the hub keeps a cursor per watch, asks the agent to start a tail when a phone subscribes and stops it when that phone leaves. A new session (after `/clear` or a `/resume` that switches) arrives as `TranscriptOpened`, which is the phone's cue to start the thread over. The "conversation cleared" divider comes from the `/clear` command line Claude writes at the head of its new file, which a `/resume` never writes.

### 3.3 Commands: idempotent, confirmed by state

- The phone mints an `IdempotencyKey` per user action and reuses it on retry.
- Hub: `CommandRouter` gives the command an id, pushes it down that machine's `Attach` stream, awaits `CompleteCommand` with a timeout.
- Agent: `CommandExecutor` checks a bounded cache of recent keys → replays the stored result instead of re-executing.
- An answer names the ask it answers, not only the pane: with two dialogs in a row on one pane, a late `Approve` would otherwise approve the second.
- The UI shows "sent" on ack and "done" only when `MachineState` shows the effect (status leaves `blocked`, a new pane appears). Lost acks never cause double prompts.
- The ack is `SendCommand`'s `CommandReceipt`. For input it carries the pane's `stateChangeSeq` as the agent read it just before sending, and "done" is `hasMovedSince(receipt, row)` on the row `WatchHerd` delivers. That read is the agent's cached `MachineState`, which follows herdr events asynchronously: a status change already in flight when the input goes out moves the row past the receipt for a reason of its own, and "done" shows early. The pending action (sent, acked, done, failed) lives in a PWA atom keyed by its `IdempotencyKey` (a launch is one screen's atom instead, see 2.7); the hub and the agent keep nothing per action beyond the agent's replay cache. A rename is done when the row's label matches the receipt's, and a close when the pane has left the herd.

### 3.4 Effect conventions (from `effect-best-practices` + `AGENTS.md`)

- Services: `Context.Service<X>()("crook/X", { make })` + a hand-written `static layer`; deps resolved with `yield*` inside `make`.
- Every method is `Effect.fn("X.method")` (automatic spans).
- One `Schema.TaggedError` per failure reason, with a full-sentence `message`. Library errors (`HerdrSocketClosed`, `TranscriptNotFound`, …) are mapped to wire errors in `@crook/protocol` at the RPC boundary, never leaked raw.
- Branded ids everywhere; `Option` for absence; no `_tag` reads.
- `Config` for every knob, `Config.redacted` for the exe.dev token.
- Each service exports a test layer next to its live one; apps compose layers once in `main.ts`.

### 3.5 Resilience

- Every long-lived connection (agent → Herdr, agent → hub, phone → hub) is a scoped resource retried with an exponential `Schedule` capped at a maximum, reset after a healthy period.
- On any reconnect the consumer re-reads authoritative state first (Herdr snapshot, `WatchHerd` first emission, transcript from last offset).
- The hub marks a machine offline when its `Attach` stream ends; it never guesses.

### 3.6 Identity and trust

- Phone: exe.dev session cookie → proxy injects `X-ExeDev-Email`; hub checks it against `CROOK_OWNER_EMAIL`.
- Agent: exe.dev VM token for the hub VM, minted with `ctx = { machine: "<id>" }`; the proxy verifies and forwards `X-ExeDev-Token-Ctx`. The hub takes `MachineId` from there only.
- The two header names live in `@crook/protocol/ExeDevHeaders`, because the hub reads them and the dev proxy (§5) writes one.
- Agent-side `CommandPolicy` is the last guard: input only to panes hosting a recognized agent; `StartAgent` only for allowed kinds.

### 3.7 PWA state

- Effect in the browser too: `RpcClient` over WebSocket, `@effect/atom-react` for state. Streaming RPCs map straight onto atoms (`WatchHerd` → herd atom, folded back into a `HerdView` by `herdViews` in the hub connection before any atom reads it; `WatchTranscript` → an atom family keyed by pane).
- The connection lifecycle is an Effect retry schedule surfaced as a `connection` atom. What the screens show (the quiet second, "Back online", what dims, what is open) rides on the link machine beside it, because those depend on what the link just went through, which a schedule doesn't know. The machine is data with a pure transition and drives nothing: the schedule and the page signals decide when to dial, and they tell it. Screens read one tagged view derived from it, so a state that dims without saying why or stays open with nothing behind it cannot be written, and the machine's walk holds that for every state.
- No XState. Multi-step flows (Ask → answer → confirm, command sent → acked → observed) are atoms holding a tagged state value, driven by `Atom.fn` effects.
- UI-local state stays in React.
- **Who owns what (JC-93).** Server state lives in atoms over one `Atom.runtime` built from the `HubLink` layer; components take values and callbacks and never read an atom; a screen reads the atoms and composes components. What only the screen cares about, such as a collapsed section, is React state. Tests swap the runtime's layer for a fake link with `Atom.initialValue`, so the real route tree renders without a socket.
- **One hub link per page.** `HubLink` holds a `SubscriptionRef` of `{ status, herd }`, where `herd` is the last `HerdSnapshot` (the view and when it arrived) and `status` is Dialing, Live, Unreachable, Offline or Expired. Every derived atom reads that one value, so the banner, the dim, the disabled actions and the badge can't disagree.
- **The cache paints first.** The last snapshot is saved to IndexedDB on every emission and loaded before the first dial, so a cold start shows the herd at once, dimmed until the hub sends a fresh one. A cache that fails to decode, such as one from an older build, is logged and ignored.
- **The socket follows the page.** The link runs only while the page is visible and the browser says it is online: hiding the page closes the socket, and showing it dials a fresh one, which is the resync on `visibilitychange`. Offline is read from `navigator.onLine` and its events, and needs no dial to detect.
- **Reconnects** back off exponentially from the agent's 77ms base, capped at the ping interval (5s). A connection that stayed live for a ping interval counts as healthy, and its drop redials at once. The schedule and the healthy rule are the agent's own, shared from `@crook/protocol/AgentLink` rather than copied. The socket pings every 5s, inside the hub's 10s silence timeout.
- **A failed dial asks whether the session expired.** It fetches `/health` with `redirect: 'manual'`: the exe.dev proxy redirects an unauthenticated request to its login, and a manual redirect comes back as an opaque response with status 0 (the Fetch standard). Status 0 shows the logged-out screen and stops dialing until the page is shown again; anything else is "hub unreachable". How the proxy answers an expired session hasn't been measured against the real proxy yet. The check is bounded by `SESSION_CHECK_TIMEOUT`, which reuses the socket's open timeout (effect's default of 10 s, not measured for this): it goes through the same proxy to the same hub right after a dial that failed, and a check that times out reads as unreachable, which is what the banner already says. The quiet second covers the dial and this check together, so a dial refused at once but checked slowly still raises the banner and the dim after a second.
- **Resync is a fresh socket**, not a second subscription: pull to resync redials and resolves once the link is live with a newer snapshot, or has failed.
- **Hub calls hold through a dial and fail when one fails.** A call made while the link dials waits for that dial, in the fiber that made it, and goes out over the new connection; when a failure lands on the banner, or after `RECONNECT_GRACE`, it fails with `HubNotConnected`. There is still no send queue: nothing outlives its caller, and the screen shows it pending until it settles. The calls of a session are handed out only once its first herd has arrived: before that the socket may still be opening, and effect's browser socket holds a write until it opens, without a bound.
- **A hub call that dies is a failed dial.** A chunk this build can't decode (a newer hub's new status, say) or a crashed hub handler reaches the client as a defect, not an error. `HubCallDefected` names it in the calls' error union, so the link shows the hub unreachable, logs why and keeps retrying, instead of freezing with no banner. A defect anywhere else in the link fails its change stream, so the app's error screen shows it.

## 4. Message flows

Startup (agent)

```
agent ── Herdr: subscribe events ──▶ then snapshot ──▶ MachineState v1
agent ── hub: Attach (ws, VM token) ◀── hub marks machine online
agent ── hub: PublishState v1 ──▶ hub ── WatchHerd ──▶ phones
```

Agent goes blocked

```
Herdr event pane.agent_status_changed ──▶ agent re-reads ──▶ MachineState v(n+1) with Ask
  ──▶ PublishState ──▶ hub: Herd updated ──▶ WatchHerd ──▶ open phones
                               └──▶ HarkNotifier (blocked) ──▶ Hark approval ──▶ lock screen
```

Approved from the lock screen

```
Hark interaction /wait resolves ──▶ HarkNotifier ──▶ CommandRouter (AnswerAsk, idempotency key = interaction id)
  ──▶ Attach ──▶ agent: CommandPolicy ──▶ send-keys ──▶ Herdr status moves on ──▶ PublishState ──▶ HarkNotifier ends the prompt
```

Answer from phone

```
phone AnswerAsk{key} ──▶ hub CommandRouter ── Attach stream ──▶ agent CommandExecutor
  ──▶ policy ──▶ herdr agent.send_keys ──▶ CompleteCommand ──▶ hub ──▶ phone "sent"
Herdr status leaves blocked ──▶ PublishState ──▶ phone "done"
```

Phone opens a chat

```
phone WatchTranscript{machine, pane, from} ──▶ hub TranscriptRelay: new watch, cursor = from
  ──▶ TranscriptDemands (whole set) ──▶ agent TranscriptStreams starts the watch
agent ── PublishTranscript{watch, Opened | Chunk} ──▶ hub: continues the cursor? ──▶ phone
                                                     └── no: TranscriptOutOfStep{expected} ──▶ agent restarts there
agent reconnects ──▶ TranscriptDemands carries each cursor ──▶ tails resume, phone stream unbroken
phone leaves ──▶ watch removed ──▶ TranscriptDemands without it ──▶ agent interrupts the tail
```

## 5. Build, run, ship

- Agent and hub: `bun build --compile` per target; the hub embeds `@crook/web`'s build output (2.6). `bun run release:build` builds the web app, then the agent and the hub for linux-x64, linux-arm64 and darwin-arm64, into `dist/` (gitignored); `bun run release:build:host` builds this machine's target only. A build replaces only the artifacts it builds, so a host build after a full one leaves the other targets in `dist/`. Bun 1.4.3 cross-compiles all three from linux-x64, downloading each target's runtime (measured). Its compile targets are `bun-linux-*` and `bun-darwin-*` for `x64` and `arm64`, each optionally `-baseline` or `-modern`, Linux ones optionally `-glibc` or `-musl`, and `bun-windows-x64` (`bun-types`). The darwin binary carries a code signature load command (read from its Mach-O header), and neither it nor the linux-arm64 one has been run on its own machine yet.
- Accepted risk: a target's Bun runtime is the one build input outside the lockfile and the action pins. Bun downloads it from the npm registry (`registry.npmjs.org`, `@oven/bun-<target>`, read from the bun binary) and caches it at `~/.bun/install/cache/bun-<os>-<arch>-v<version>` (measured); nothing here pins its checksum, and the signed `SHA256SUMS` covers only what comes out. Bun pinned to 1.4.3 narrows it. Compiling each target on a runner of its own kind, or pinning each runtime's checksum, would close it.
- The compiled binaries turn off Bun's `.env` and `bunfig.toml` autoload, which default on and read the working directory (`bun build --help`, 1.4.3): a daemon started from a project folder would take that folder's settings. Configuration comes from the environment the unit sets. Both answer `--version` with `crook-<app> v<version>`.
- Agent runs as a systemd user unit (`crook-agent.service`, a launchd agent on macOS) running `crook-agent run`, installed by `crook-agent install-service` (2.5, "Service install") or the plugin's "connect" action.
- Hub runs as a systemd unit on its own exe.dev VM.
- Releases come from `.github/workflows/release.yml` on a pushed `vX.Y.Z` tag, and only then: no branch push runs it. `gate` first fails unless the tagged commit is on `main` (`git merge-base --is-ancestor`, over a full-history checkout), so a tag on an unmerged branch publishes nothing and release authority is the right to push a tag on a merged commit. It then runs `crook-release check-version` (the tag is `v` and a plain version, and the agent and the hub are both at it), then the four gate steps. `publish` builds every target, runs the runner's own linux-x64 pair through `packages/release/smoke.sh` (both binaries report the tag's version, and the hub, started on a throwaway database with `CROOK_WEB_ROOT` unset, serves `/` with its Content-Security-Policy and the page's first script with its immutable Cache-Control from the embedded build), writes `SHA256SUMS` over the binaries and the installer, signs it, verifies that signature with the exact identity and issuer `install.sh` demands, and only then creates the GitHub release with all of them: a release its own installer refuses could only be replaced by cutting another tag. Every action is pinned by commit SHA, looked up with `gh api`, with its version in a trailing comment.
- Signing is cosign keyless (Sigstore) with the workflow's GitHub OIDC token. No private key exists to create, keep in a secret, rotate or leak, and the certificate names the workflow and the tag that signed, so the installer demands exactly `https://github.com/jliocsar/crook/.github/workflows/release.yml@refs/tags/v<version>` from `https://token.actions.githubusercontent.com`. A signature made for another tag, workflow or repository fails, and so does a changed file (measured with cosign 3.0.6 against goreleaser's release, which signs its checksums the same way). The cost: Fulcio's certificate and the Rekor entry are public, so the repository's name, the tag, the commit and the artifacts' digests become public although the repository is private. One signature covers `SHA256SUMS`, and each binary is checked against it.
- The installer is `packages/release/install.sh`, attached to every release: `install.sh [--version X.Y.Z] [agent] [hub]`, the agent and the latest release by default. It downloads with `gh` when present (the repository is private) or `curl`. With `gh` it reads the release and fetches each asset through `gh api`'s REST endpoints, so `GH_HOST=github.int.exe.xyz` reaches the repository through an exe.dev GitHub integration on a VM with no GitHub login; `gh release download` follows the asset's `api.github.com` URL and gets a 404 there (measured). It checks the signature with cosign 3.0.6, downloaded once into `~/.cache/crook` and checked against the SHA-256 the `sigstore/cosign-installer` action pins, which cosign's own checksums file matches (`CROOK_COSIGN` names another cosign to trust); checks each binary against the signed checksums; runs it with `--version` and expects the release's own; and only then installs into `~/.local/bin` (`CROOK_INSTALL_DIR`) by copy and rename, so a running binary is replaced rather than written over. Downloads go to a directory under `~/.cache/crook`, where the cached cosign already runs, rather than `$TMPDIR`, which a machine may mount noexec, since each binary runs once from there. Nothing updates on its own: the installer runs only when the user runs it.
- The Herdr plugin's update path (JC-113) runs this same installer with the version the user picks, and runs no `install.sh` it has not checked. Two would qualify: the one in its own checkout of this repository, which is as trusted as the plugin, and one downloaded from the release and checked against the signed `SHA256SUMS` (which lists `install.sh` for exactly this) before it runs. It runs the one in its checkout, because herdr installs the plugin as a shallow checkout of the whole repository (measured, 2.5), so the installer is already there. For a person who downloads and runs `install.sh` by hand, its checksum protects nothing, since it has run before anything checks it.
- Locally, the web app talks to a real hub through Vite's dev server: with `CROOK_DEV_HUB_URL`, `CROOK_OWNER_EMAIL` and `CROOK_HUB_ORIGIN` set, `bun run dev` proxies `/rpc/client` and `/health` to that hub, and `bun run preview` does the same so a production build runs under the CSP against it. On the socket it adds the `X-ExeDev-Email` and `Origin` the exe.dev proxy would send, and only when the upgrade's `Host` is a loopback name (`localhost`, `127.0.0.1`, `[::1]`) and its `Origin` is that same host and port: browsers let any page open a WebSocket to localhost, and a proxy that vouched for every upgrade would walk a stranger's page past the hub's Origin check as the owner. Matching `Origin` to `Host` alone is not enough, since a DNS-rebound page sends both under its own name, and Vite's `allowedHosts` does not cover a proxied upgrade. A refused upgrade is still forwarded, bare, and the hub answers it with 403. `/health` gets no headers, since the hub needs none there. It is dev tooling in the Vite config only; nothing in the app knows about it. The hub needs no local mode for it.

## 6. Testing

- Pure modules (`claude` parser, `deriveAsk`, domain mapping) get fixture-driven tests from captured real sessions.
- Services are tested against their `layerTest` siblings; RPC handlers with `RpcTest` (in-memory).
- One end-to-end check per milestone: fake Herdr (test layer) → real agent → real hub → headless RPC client.
- The check lives in the hub's tests (JC-94), not a member of its own. The hub's test fixtures already serve the real hub on a local port and dial it over real WebSockets with the NDJSON serialization, and the hub already dev-depends on the agent for its command test. A separate member would have had to serve the hub again or move those fixtures into a source module. It runs the agent's own `MachineStateSync`, `PendingAsks` (the ask derived from the pane's screen), `CommandExecutor` and `HubLink` over `HerdrClient.layerTest`, and takes test layers only where the agent reads the host: `/proc`, git, the hook socket, recent places, created panes. It covers a herdr status change reaching `WatchHerd`, the change travelling as that machine's `MachineReplaced`, with no `HerdReplaced` and nothing for a second, quiet machine on the way, a `Prompt` reaching herdr as `agent.prompt` with its receipt back, and an `AnswerAsk` on the ask the phone read from the herd, answered with the keys herdr presses.
- The scripted herdr fake answers each method by how many times it has been asked, repeating the last answer. A test that needs herdr's answer to change at a moment it picks swaps between two scripted fakes behind one client (`HerdrClient.makeSwitchingTest`), then sends the event. That fake lives in `@crook/herdr` beside `layerTest`. The herdr record builders (`@crook/herdr/fixtures/Records.ts`) stay in the member's test fixtures, which the agent's tests and the hub's end-to-end check reach through its `./fixtures/*` export. Scripting by count races: the agent coalesces herdr events behind a sliding buffer, so how many reads happen before the event is not fixed.
